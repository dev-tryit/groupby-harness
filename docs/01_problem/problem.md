# 문제 정의

근거는 `00_context/context.md`다. 과제의 문장에서 출제자의 의도를 읽고, 우리가 풀어야 하는 문제를 적는다. 어떻게 풀지는 이 문서에서 정하지 않는다.

## 1. 결론: 우리가 풀어야 하는 문제

공고(비정형 이미지)에서 조건을 뽑고, 그 조건과 이력서를 비교해 지원자가 조건을 충족하는지 판정하고, 사람이 확인할 수 있는 점수와 근거를 내는 문제다.

### 1.1 만들 서비스

고객사의 채용 담당자가 공고를 넣으면, 지원자들의 랭킹과 근거를 받는 서비스다. 고객사(서비스를 쓰는 기업)를 위한 B2B 서비스다.

1. 고객사 쪽에서 사람인의 이미지 공고를 가져온다. 사람인에 접속하는 것은 서비스 제공사의 서버가 아니라 고객사다.
2. 이미지를 읽어 조건을 뽑는다.
3. 서비스가 조건과 지원자들의 이력서를 비교해 0~100점과 랭킹을 낸다.
4. 채용 담당자가 점수의 근거를 보고 동의하거나 고친다.
5. 그 판단이 데이터로 남아 검증과 개선에 쓰인다.

고객사 쪽과 서비스 제공사의 서버 사이의 경계는 이렇다.

```
[고객사 쪽]  수집 → 읽기  ──(고객사가 넘긴 것)──▶  [서비스 제공사의 서버]  조건 추출 → 비교 → 점수 → 근거
```

- 수집은 고객사 쪽에서 일어난다. 이것은 정했다.
- 읽기(이미지 → 글자)도 고객사 쪽에서 일어난다. 서비스 제공사의 서버는 읽은 글자만 받고, 공고의 이미지는 받지 않는다.

B2B로 본 이유는 세 가지다.

- 과제가 "고객사"라는 말을 쓴다. 서비스 제공사의 고객이 기업이라는 뜻이다.
- 공고 하나에 지원자 여러 명을 매칭하고 랭킹하는 것은 채용 담당자가 하는 일이다.
- 과제는 서비스 제공사가 크롤링해서 직접 적재하는 것이 문제라고 했고, 데이터가 고객사를 거쳐서 들어오게 하라고 했다. 크롤링을 없애라는 것이 아니라, 가져오는 주체를 고객사로 바꾸라는 것으로 읽었다. 기준은 데이터가 어디에 있느냐가 아니라 누가 가져와서 넣었느냐다.

### 1.2 풀어야 하는 문제

```
[공고]    수집 → 읽기 → 조건 추출 ─┐
                                   ├→ 비교(판정) → 점수 → 근거 → 사람의 판단 → 데이터
[이력서] ──────────────────────────┘        ↑                                   │
                                             └──────── 검증과 개선 ──────────────┘
```

풀어야 하는 문제는 여덟 가지다.

| 단계 | 풀어야 하는 문제 |
| :- | :- |
| 1. 수집 | 사람인의 이미지 공고를 공식 API 없이 가져와야 한다. |
| 2. 읽기 | 이미지에 적힌 내용을 틀리지 않게 읽어야 한다. |
| 3. 조건 추출 | 읽은 내용에서, 어떤 직군의 공고든 조건을 뽑아야 한다. |
| 4. 비교(판정) | 공고의 조건과 이력서를 비교해, 표현이 달라도 지원자가 조건을 충족하는지 알아야 한다. |
| 5. 점수 | 판정을 사람이 납득할 수 있는 0~100점으로 만들어야 한다. |
| 6. 근거 | 근거마다 출처(공고의 어느 조건, 이력서의 어느 구절)를 가리켜, 사람이 직접 확인할 수 있어야 한다. |
| 7. 검증 | 근거가 사실인지, 점수가 그 근거에서 나왔는지를 확인할 수 있어야 한다. |
| 8. 피드백 | 사람이 근거를 보고 내린 판단이 데이터로 남아, 다음 검증과 개선에 쓰여야 한다. |

전체에 걸친 제약은 세 가지다.

| 제약 | 내용 |
| :- | :- |
| 직군 무관 | 특정 직군이나 스킬에 기대지 않아야 한다. |
| 비용 | 약 $5의 예산 안에서 개발과 평가자의 실행이 모두 되어야 한다. |
| 법 | 서비스 제공사가 채용 정보를 직접 적재하지 않고, 데이터가 고객사를 거쳐 들어오는 구조여야 한다. |

### 1.3 용어

문제를 정의하기 전에 지원자가 내는 문서가 무엇인지부터 정한다. 통념으로 본 정의다.

| 문서 | 담는 것 | 지원자가 보여 주려는 것 | 고객사가 보려는 것 |
| :- | :- | :- | :- |
| 이력서 | 사실의 목록 (학력, 경력, 자격증, 보유 기술, 기간) | 무엇을 갖췄고 무엇을 해 왔는가 | 자격요건을 채우는가, 해 본 사람인가 |
| 경력기술서 | 경험의 내용 (맡은 역할, 한 일, 결과) | 그 일을 어떻게, 얼마나 했는가 | 경험의 깊이 |
| 자기소개서 | 사람에 대한 서술 (지원 동기, 성격, 일하는 방식, 포부) | 어떤 사람이고 왜 지원했는가 | 성향, 동기 |
| 포트폴리오 | 결과물 (만든 것 자체) | 실제로 이만큼 할 수 있다 | 경험의 증거, 수준 |

과제가 말하는 것은 이력서다. 자기소개서와 포트폴리오는 과제에 없다.

## 2. 출제자의 의도

이 과제는 그룹바이 실제 제품의 축소판이고, 결과물이 아니라 판단을 보려는 것이다. 그래서 **우선순위가 곧 답안**이다. 무엇을, 왜, 어떻게 했는지를 보여주는 데 집중한다.

| 과제의 문장 | 읽은 의도 |
| :- | :- |
| "전부 완성하지 못해도 괜찮다, 우선순위를 정해서" | 무엇을 하고 무엇을 버렸는지를 본다. |
| "전체 흐름을 먼저 잇고, 핵심부터" | 무엇을 핵심으로 골랐는지를 본다. |
| 이미지 공고, 복붙 금지, 공식 API 금지 | 현실의 비정형 데이터를 다루는지를 본다. |
| "추출값을 조건으로 바로 세팅" | 공고에서 조건을 만드는 것을 본다. |
| 직군 무관, 하드코딩 금지, 서로 다른 직군 2개 | 직군에 대한 이해를 쓰지 않고 일반화하는지를 본다. |
| 0~100점과 랭킹 | "잘 매칭됐다"를 어떻게 정의하는지를 본다. |
| 점수의 근거를 사람이 읽게 | 채용 담당자가 점수를 믿을 수 있는지를 본다. |
| 완벽 2, 부분 3, 미스매치 1 | 평가셋을 직접 설계하는지를 본다. |
| "어떤 케이스를 테스트로 골랐는지를 본다" | 시스템이 어디서 깨지는지 아는지를 본다. |
| 법적 우회 구조 (구현 불필요) | 코드 밖의 사업 감각을 본다. |
| 예산 약 $5 | LLM을 어디에 쓰고 어디에 쓰지 않을지를 본다. |
| "README는 직접", "어떤 판단을 더했는지" | 스스로 문제를 정의하고 해결하는지를 본다. |

## 3. 과제가 비워 둔 것

과제는 아래 세 가지를 정의하지 않았다. 이것을 채우는 것이 문제 정의다.

- "잘 매칭됐다"가 무엇인지
- "부분 매칭"이 무엇이 부분인지
- 0~100점이 무엇을 뜻하는지

## 4. 문제를 이렇게 본 이유

### 4.1 조건이 중심축이다

공고를 넣으면 조건이 자동으로 만들어지고, 점수와 근거는 그 조건을 기준으로 나온다. 조건이 공고와 지원자를 잇는다.

### 4.2 직군이 아니라 조건의 형식을 일반화해야 한다

세상에 어떤 직군이 얼마나 있는지 알 수 없다. 그래서 직군에 대한 이해에 기댈 수 없다. 어떤 공고에서든 유의미한 특징을 뽑아내는 특징 추출기가 필요하다. 과제가 서로 다른 직군의 공고 2개를 요구한 것은 이 일반화를 확인하기 위해서라고 본다.

### 4.3 점수는 사람이 납득할 수 있는 수치여야 한다

LLM이 내놓은 숫자는 그럴듯한 말일 뿐 실제 수치가 아니다.

### 4.4 매칭에는 객관적인 정답이 없다. 그래서 근거가 중요하다

- 매칭이 옳은지의 기준은 사람의 판단이다. 진짜 검증은 사람들에게 물어야 한다.
- 점수만 있으면 사람은 믿거나 믿지 않거나 둘 중 하나다. 근거가 있으면 사람이 직접 확인하고 동의하거나 반박할 수 있다.
- 그래서 풀어야 하는 문제는 "맞음을 증명한다"가 아니라 "사람이 확인할 수 있게 한다"이다.

### 4.5 검증은 두 겹이다

| | 무엇을 확인하는가 | 언제 |
| :- | :- | :- |
| 지금 하는 검증 | 근거가 사실인지, 골든셋의 가설대로 움직이는지 | 코드를 만들 때 |
| 플라이휠이 하는 검증 | 사람의 판단과 일치하는지 | 서비스가 쓰이면서 |

- 골든셋은 정답이 아니다. 검증하려는 가설을 증명하는 데이터다. 그래서 골든셋을 구축하는 일이 중요하다.
- 사람의 판단과 일치하는지는 이 과제 안에서 증명할 수 없다. 그래서 사람의 판단을 받는 UI/UX까지 표현해, 그 판단이 데이터로 쌓이는 데이터 플라이휠이 굴러가게 해야 한다.

### 4.6 비용에 제한이 있다

예산에 제한이 있으므로 LLM을 막 쓸 수 없다. 결정론적으로 할 수 없는 일에 쓴다. 쓰기 전에 비용이 얼마나 나오는지부터 확인한다.

### 4.7 수집은 핵심 문제가 아니다

- 이 서비스에서 공고는 고객사가 넘기는 것이다(1.1). 서비스 제공사의 서버는 고객사가 넘긴 것을 받는다. 그래서 여덟 가지 문제 가운데 수집은 핵심이 아니다.
- 핵심은 그 뒤다. 조건을 어떻게 뽑고, 어떻게 비교하고, 점수와 근거를 어떻게 내는지다.
- 그 가운데 가장 많이 고민해야 하는 것은 읽기(OCR)와, 직군에 기대지 않는 일반화된 조건 추출이다. 조건이 중심축이므로(4.1), 여기서 틀리면 그 뒤의 비교, 점수, 근거가 모두 틀린다.
- 비교(판정)도 고민해야 한다. 비교는 조건이 어떤 구조로 나오느냐에 따라 달라지므로, 조건 추출 다음에 고민한다.
- 과제가 크롤링을 요구하고 전체 흐름이 처음부터 끝까지 이어져야 하므로 수집을 없애지는 않는다. 적당한 공고를 가져와 데이터를 확보하는 데까지만 한다. 공고 주소 하나를 받아 본문 이미지를 가져오고, 고른 공고 2개에서 동작하면 된다.
- 목록 수집, 차단 회피, 어떤 공고든 대응하는 견고함은 만들지 않는다.

### 4.8 채용 공고와 이력서의 매칭 문제로 본다

사용자의 결정이다. 조사는 `02_research/screening/screening.md`에 있다.

- 이 과제는 채용 공고와 이력서를 매칭하는 문제다. 그 이상으로 넓히지 않는다.
- 결국 고객사가 만족해야 한다. 서비스를 쓰는 쪽이 고객사이기 때문이다. 그래서 고객사가 지원자를 검토할 때 어떤 항목들을 어떤 순서로 바라보는지를 조사했다.
- 가설: 회사가 원하는 것은 채용 공고에 배어 있다. 스타트업과 대기업의 차이는 크게 체계가 있느냐 없느냐일 것이고, 초창기 기업은 일당백을 원하며, 그다음 단계의 기업은 점차 체계를 잡아 가면서 이 사람이 교체되었을 때까지 생각하는 경향이 있다. 창업자의 방식에 따라서도 다르다. 이렇게 회사마다 다른 원하는 바가 공고에 배어 있다고 본다. 그래서 회사의 규모를 따로 알 필요가 없고 공고가 기준이다.
- 가설: 고객사가 만족하려면 결국 지원자가 만족하는 것도 중요하다. 무게는 비유로 말하면 고객사 7, 지원자 3 정도다(숫자에는 의미가 없다).
- 이것은 문제를 보는 가설이고, 무엇을 만들라는 지시가 아니다. 만드는 범위는 채용 공고와 이력서의 매칭이다.

### 4.9 면접 전의 적합도를 찾는다. 면접 때 보는 것은 점수로 계산하지 않는다

사용자의 가설이다. 조사는 `02_research/screening/screening.md` 3.3에 있다.

- 고객사가 지원자에게서 보는 것은 자격요건, 경험, 성향이다.
- 면접은 그 사람을 직접 보고 판단하려고 하는 것이다. 그렇다면 서류전형은 서류로 적합도를 판단하는 것이다.
- 그래서 면접 때 보는 것(성향)은 매칭 여부만 적당히 보여 주고, 점수로 계산하지 않는 것이 좋다.
- 인재상이 그런 특징이다. 인재상도 중요하다. 다만 점수에 계산하지 않고, 안내 사항으로 보여 주면 좋은 특징이다.
- 전형 절차도 중요하지만 이력서와 맞춰 볼 지점이 없다.
- 면접 전의 적합도를 찾으면 매칭이 더 납득된다. 서비스가 그 사람 속으로 들어간 것이 아니기 때문이다.

### 4.10 읽은 결과 전체를 버리지 않고, 전체에서 조건을 뽑는다

사용자의 결정이다.

- 채용 공고 전체를 읽은 값(OCR 결과)은 버리지 않는다. 일부만 골라 읽거나, 읽은 뒤에 일부를 지우지 않는다.
- 중요한 것은 그 전체를 기준으로, 우리가 원하는 형태로 조건을 뽑는 일이다.
- 개발 직군 위주로 생각하면 안 된다. 일반화의 관점에서 봐야 한다(4.2). 공고의 어느 부분에 무엇이 적혀 있을지를 직군에 맞춰 미리 정해 두지 않고, 전체에서 뽑는다.

| 미뤄 두었던 것 | 정한 것 | 정한 곳 |
