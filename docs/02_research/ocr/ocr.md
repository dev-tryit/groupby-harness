# 읽기(OCR) 조사

공고의 본문 이미지를 글자로 읽는 방법과, 그 성능과 비용을 조사한 문서. 근거는 `01_problem/problem.md`의 1.1(경계 도식), 4.6(비용), 4.7(읽기가 핵심), 5장(아직 정하지 않은 것)이다.

이 문서는 공식 문서, 논문, 공개된 글을 읽고 정리한 자료 조사다. 직접 잰 것이 아니다. OpenAI API를 호출하지 않았고, 어떤 OCR 엔진도 실제 공고 이미지에 돌려 보지 않았다. 비용은 공식 가격표와 공식 토큰 계산 규칙에 가정을 넣어 계산한 값이다. 확인한 날짜는 2026-10-10이다.

## 1. 결론

- 읽는 방법은 세 갈래다. 로컬 OCR 엔진, 클라우드 OCR, LLM의 이미지 읽기다. 과제의 키는 OpenAI뿐이므로 실제 후보는 로컬 OCR 엔진과 OpenAI 비전 모델이다.
- 비용은 걸림돌이 아니다. 가정한 공고 한 건(가로 900 × 세로 6000픽셀 분량)을 OpenAI 비전 모델로 읽는 비용은 모델에 따라 약 $0.005 ~ $0.06이다(3장). 가장 싼 축은 `gpt-5.4-nano`와 `gpt-5.6-luna`(약 $0.005), 그다음이 `gpt-4.1-mini`(약 $0.01)다. 로컬 OCR 엔진은 $0다.
- 걸림돌은 정확도와 충실성이다. 공개 자료에서 로컬 OCR 엔진은 한국어 글자를 더 많이 틀리고, LLM은 글자를 덜 틀리지만 흐릿하거나 낯선 글자를 그럴듯한 글자로 바꿔 쓴다(4장). 어느 쪽도 그대로 믿을 수 없다.
- 세로로 긴 이미지는 그대로 보내면 안 되는 모델이 있다. `gpt-4o`, `gpt-4.1`, `gpt-4.1-mini` 등은 긴 변을 2048픽셀로 줄이므로 900 × 6000 이미지가 307 × 2048로 줄어 글자가 약 1/3 크기가 된다. 잘라서 보내야 한다. `gpt-5.4` 계열 이상은 `detail: original`로 줄이지 않고 받을 수 있다(3.2).
- `gpt-4o-mini`는 싼 선택이 아니다. 이미지 토큰이 `gpt-4o`의 약 33배로 잡혀서 이미지 입력 비용이 `gpt-4o`와 거의 같다(3.2).
- 추천 후보는 세 가지다. 정하는 것은 사용자다.
  1. **로컬 OCR 엔진(PaddleOCR의 한국어 모델)으로 글자와 좌표를 얻고, LLM은 글자를 입력으로 조건 추출만 한다.** 읽기가 결정론적이고 좌표가 남는다. 읽기의 정확도가 낮을 위험이 있다.
  2. **OpenAI 비전 모델(싼 축의 모델)이 잘라 낸 이미지를 읽는다.** 글자 정확도와 표·배치 보존이 좋을 가능성이 높다. 좌표가 없고, 바꿔 쓰기와 빠뜨리기를 따로 잡아야 한다.
  3. **둘을 함께 쓴다.** 로컬 OCR 엔진의 글자와 좌표를 LLM이 읽은 결과와 교차 확인한다. 두 결과가 다른 곳을 "확인 필요"로 표시한다. 비용은 2번과 같고 구현이 가장 많다.
- 읽기의 자리(고객사 쪽/서버)는 방법과 묶여 있다. 로컬 OCR 엔진은 고객사 쪽에 둘 수 있다. OpenAI 비전 모델은 API 키가 필요해서 고객사 쪽에 두기 어렵다(7장).
- 세 후보의 우열은 실제 공고 이미지로 재야 알 수 있다. 직접 잴 때의 계획은 8장에 있다.
- 2026-10-11에 로컬 OCR 엔진 두 가지를 실제 공고 이미지 8건으로 쟀다. 조건 줄 64개(947자)에서 PaddleOCR의 글자 오류율은 0.4%, EasyOCR은 7.1%였다. PaddleOCR은 글자는 거의 틀리지 않았고, 띄어쓰기와 읽는 순서와 표의 칸 경계를 잃었다. OpenAI의 모델은 같은 날 사용자가 키를 쓰도록 허락해서 쟀다(11.11). `gpt-4.1-mini`(온도 0)는 조건 줄 64개를 두 번 모두 맞게 읽었고 결과가 거의 같았다. `gpt-5.6-luna`는 글자를 그럴듯하게 바꿔 썼고 읽을 때마다 달라졌다. 사용자는 OpenAI의 모델로 읽기로 했다. 엔진을 여섯 가지로 늘려 공고별로 견준 표는 11.7에 있다. 로컬 엔진 가운데 후보로 남는 것은 PaddleOCR이고, 에이전트(Claude)가 직접 읽은 것과의 글자 차이는 2,688자 가운데 9~14자였다.

## 2. 방법 후보 비교

### 2.1 로컬에서 도는 OCR 엔진

| 엔진 | 한국어 | 표·배치 | 좌표·신뢰도 | 실행 부담 | 라이선스 |
| :- | :- | :- | :- | :- | :- |
| Tesseract 5 | 지원한다(`kor` 학습 데이터). | 표를 읽는 기능이 없다. 공식 문서가 "표의 글자를 인식하는 데 알려진 문제가 있다"고 적었다. 여러 단은 기본 분할 모드로 처리한다. | TSV와 hOCR 출력에 단어마다 상자와 신뢰도가 있다. | CPU만으로 돈다. 설치가 가장 가볍다(크기는 확인하지 못했다). | Apache-2.0 |
| PaddleOCR (PP-OCRv5) | 지원한다. 한국어 인식 모델은 `korean_PP-OCRv5_mobile_rec`이고 `lang="korean"`으로 부른다. | PP-OCR 자체는 글자 줄만 준다. 표와 배치는 PP-StructureV3가 맡는다. | 줄마다 다각형 좌표와 점수(`rec_polys`, `rec_scores`)를 준다. | CPU로 돈다. 공식 문서의 모듈별 CPU 시간은 검출 약 58ms, 인식 약 21ms다(Xeon Gold 6271C, 8스레드, 모바일 모델). 이미지 한 장 전체의 시간과 Docker 이미지 크기는 확인하지 못했다. | Apache-2.0 |
| PaddleOCR (PP-StructureV3) | PP-OCR의 언어 설정을 따른다. | 배치 영역(제목, 본문, 표 등), 여러 단의 읽기 순서, 표의 셀 좌표를 준다. 마크다운과 JSON으로 저장한다. | 영역마다 상자와 점수를 준다. | 모델이 여러 개 붙어 무겁다. 배치 모델 약 126MB(CPU 약 635ms), 표 구조 모델 약 351MB(CPU 약 502ms)다. | Apache-2.0 |
| EasyOCR | 지원한다(코드 `ko`). | 없다. | 상자 네 꼭짓점, 글자, 신뢰도를 준다. | CPU로 돈다(`gpu=False`). PyTorch에 의존해 설치가 크다. 마지막 릴리스가 2024-09-24(1.7.2)다. | Apache-2.0 |
| Surya | 지원한다. 자체 벤치마크의 한국어 통과율이 86.7%다. | 배치 분석, 읽기 순서, 표의 행·열(HTML 출력)을 지원한다. | 블록마다 상자와 다각형을 준다. | 약 6억 5천만 파라미터의 모델이다. GPU를 전제로 한 수치만 있고, Apple Silicon에서 약 0.1쪽/초다. 일반 x86 CPU의 속도는 확인하지 못했다. | 코드는 Apache-2.0이다. 모델 가중치는 별도 라이선스이고, 연 매출이나 투자금이 $5M 이상이면 상업 라이선스가 필요하다. |
| docTR | **지원하지 않는다**(2026년 논문이 "한국어와 중국어를 지원하지 않는다"고 적었다). | - | - | - | - |

- 해석: 과제의 실행 조건(평가자의 PC, Docker Compose, CPU)에 맞는 것은 Tesseract와 PaddleOCR(PP-OCRv5)다. Surya는 CPU에서 느릴 가능성이 높고, docTR은 한국어가 안 되므로 후보에서 뺀다. EasyOCR은 표·배치 기능이 없고 갱신이 멈춰 있어 PaddleOCR보다 나은 점을 찾지 못했다.
- PaddleOCR에는 문서 전용 소형 VLM인 PaddleOCR-VL(약 9억 파라미터, 한국어 지원)도 있다. CPU에서의 속도는 확인하지 못했다.

- 해석: 서비스가 실제로 운영된다면 클라우드 OCR이 유력한 후보다. 건당 가격이 OpenAI 비전 모델의 싼 축과 비슷하거나 더 싸고, 좌표와 신뢰도를 준다. 이 과제에서는 키가 없어 쓰지 않는다.

### 2.3 LLM의 이미지 읽기 (OpenAI)

OpenAI 공식 가격표(2026-10-10 확인)의 표준 요금이다. 단위는 토큰 100만 개당 달러다. 이미지 토큰은 모델의 입력 가격으로 계산한다.

| 모델 | 입력 | 출력 | 이미지 토큰 계산 방식 |
| :- | -: | -: | :- |
| `gpt-5.4-nano` | $0.20 | $1.25 | 패치(32픽셀), 배수 1.2 |
| `gpt-5.6-luna` | $0.20 | $1.20 | 패치, 배수 1.2 |
| `gpt-4.1-mini` | $0.40 | $1.60 | 패치, 배수 1.62 |
| `gpt-5.4-mini` | $0.75 | $4.50 | 패치, 배수 1.2 |
| `gpt-4o-mini` | $0.15 | $0.60 | 타일(512픽셀), 기본 2833 + 타일당 5667 |
| `gpt-5.1` | $1.25 | $10.00 | 타일, 기본 70 + 타일당 140 |
| `gpt-4.1` | $2.00 | $8.00 | 타일, 기본 85 + 타일당 170 |
| `gpt-5.6-terra` | $2.00 | $12.00 | 패치, 배수 1.2 |
| `gpt-4o` | $2.50 | $10.00 | 타일, 기본 85 + 타일당 170 |
| `gpt-5.4` | $2.50 | $15.00 | 패치, 배수 1.2 |

- 가격표에는 `gpt-6-luna`($0.10 / $0.50), `gpt-6-sol`과 `gpt-6.1-sol`($2.00 / $10.00), `gpt-6-astra`($10.00 / $50.00)도 있다. 이 가운데 `gpt-6-astra`만 이미지 토큰 계산 표에 있고, 나머지 셋은 표에 없어서 이미지 비용을 계산하지 못했다.
- `gpt-5-mini`, `gpt-5-nano`, `gpt-4.1-nano`는 공식 문서가 지원 종료 예정으로 표시했고 크기 조정 규칙을 싣지 않았다. 후보에서 뺀다.
- LLM은 좌표를 주지 않는다. 공식 문서가 "정밀한 위치 파악이 필요한 일에 약하다"고 적었다.
- 공식 문서의 한계 항목에 "일본어나 한국어처럼 라틴 문자가 아닌 글자가 있는 이미지에서는 성능이 최적이 아닐 수 있다"가 있다. 작은 글자에 대해서는 "이미지 안의 글자를 키우라", "`detail: original`이 도움이 될 수 있다"고 적었다.

## 3. 비용 계산

### 3.1 가정

| 항목 | 가정 | 이유 |
| :- | :- | :- |
| 공고 한 건의 이미지 | 가로 900 × 세로 6000픽셀 한 장 분량 | 과제 설명의 예를 따랐다. 실제 사람인 공고의 크기는 재지 않았다. |
| 자르는 방식 | 세로 1000픽셀씩, 150픽셀 겹침 → 7조각 (900 × 1000) | 겹침은 잘린 줄을 다시 읽기 위한 것이다. (6000 − 1000) ÷ 850 = 5.9이므로 7조각이다. |
| 지시문 | 호출 한 번에 300토큰 | 가정이다. |
| 출력 | 공고 한 건에 3,000토큰 | 가정이다. 한글 2,000자 안팎과 표 표기를 넉넉히 잡았다. 한글 한 글자가 몇 토큰인지는 재지 않았다. |
| 추론 토큰 | 0 | `gpt-5` 계열은 추론 토큰이 출력으로 청구될 수 있다. 얼마나 나오는지 확인하지 못했다. 이 가정이 틀리면 출력 비용이 늘어난다. |

### 3.2 이미지 한 장의 토큰

공식 문서의 규칙이다.

- 타일 방식(`gpt-4o`, `gpt-4.1`, `gpt-4o-mini`, `gpt-5.1`): ① 2048 × 2048 안에 들어가게 줄인다. ② 짧은 변이 768픽셀보다 크면 768픽셀로 줄인다. ③ 512픽셀 정사각형 타일의 수를 센다. ④ 토큰 = 기본 + 타일 수 × 타일당 토큰. `detail: low`는 크기와 무관하게 기본 토큰만 든다.
- 패치 방식(`gpt-4.1-mini`, `gpt-5.4` 계열 이상): ① detail 단계의 최대 변 길이 안에 들어가게 줄인다. ② 패치 수 = ceil(가로 ÷ 32) × ceil(세로 ÷ 32). ③ 패치 예산을 넘으면 더 줄인다. ④ 토큰 = ceil(패치 수 × 배수). 처리 후 30,000패치를 넘는 이미지는 요청이 거부된다.
- 패치 방식의 detail 단계별 한도는 모델마다 다르다.

| 모델 | high | original | 기본값(auto) |
| :- | :- | :- | :- |
| `gpt-4.1-mini` | 최대 변 2048픽셀, 6,144패치 | 지원하지 않는다 | high와 같다 |
| `gpt-5.4`, `gpt-5.4-mini`, `gpt-5.4-nano` | 최대 변 2048픽셀, 2,500패치 | 최대 변 6000픽셀, 10,000패치 | high와 같다 |
| `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna` | 2048 × 2048픽셀, 2,500패치 | 줄이지 않는다(한 변 65,535픽셀까지) | original과 같다 |

이 규칙으로 계산한 결과다.

| 보내는 이미지 | 모델·설정 | 모델이 보는 크기 | 계산 | 토큰 |
| :- | :- | :- | :- | -: |
| 900 × 6000 한 장 | `gpt-4o`, `gpt-4.1` (high) | **307 × 2048** | 타일 1 × 4 = 4, 85 + 4 × 170 | 765 |
| 900 × 6000 한 장 | `gpt-4.1-mini` | **307 × 2048** | 10 × 64 = 640패치 × 1.62 | 1,037 |
| 900 × 6000 한 장 | `gpt-5.4` 계열 (high 또는 auto) | **307 × 2048** | 640패치 × 1.2 | 768 |
| 900 × 6000 한 장 | `gpt-5.4` 계열 (original) | 900 × 6000 | 29 × 188 = 5,452패치 × 1.2 | 6,543 |
| 900 × 6000 한 장 | `gpt-5.6` 계열 (auto) | 900 × 6000 | 5,452패치 × 1.2 | 6,543 |
| 900 × 1000 조각 | `gpt-4o`, `gpt-4.1` (high) | 768 × 853 | 타일 2 × 2 = 4, 85 + 4 × 170 | 765 |
| 900 × 1000 조각 | `gpt-4o-mini` (high) | 768 × 853 | 2833 + 4 × 5667 | 25,501 |
| 900 × 1000 조각 | `gpt-5.1` (high) | 768 × 853 | 70 + 4 × 140 | 630 |
| 900 × 1000 조각 | `gpt-4.1-mini` | 900 × 1000 | 29 × 32 = 928패치 × 1.62 | 1,504 |

읽을 수 있는 것은 세 가지다.

- 900 × 6000 이미지를 자르지 않고 보내면 `gpt-4o`, `gpt-4.1`, `gpt-4.1-mini`, 그리고 `detail`을 지정하지 않은 `gpt-5.4` 계열에서 가로가 307픽셀로 줄어든다. 글자가 약 1/3 크기가 된다. 토큰이 적게 나오는 것은 싸서가 아니라 글자가 뭉개졌기 때문이다(해석).
- `gpt-5.4` 계열은 세로 6000픽셀이 `original`의 최대 변 한도(6000픽셀)와 정확히 같다. 세로가 6000픽셀을 넘는 공고는 줄어든다. 넘는 공고는 잘라야 한다.
- `gpt-4o-mini`는 조각 하나에 25,501토큰이다. 입력 가격($0.15)을 곱하면 조각당 $0.0038이고, `gpt-4o`의 조각당 $0.0019보다 비싸다.

### 3.3 공고 한 건을 읽는 비용

식은 `(이미지 토큰 + 지시문 토큰) × 입력 가격 + 출력 토큰 × 출력 가격`이다.

| 모델 | 보내는 방식 | 입력 토큰 | 입력 비용 | 출력 비용 | 공고 한 건 | 공고 2건 |
| :- | :- | -: | -: | -: | -: | -: |
| `gpt-5.6-luna` | 한 장, auto | 6,843 | $0.0014 | $0.0036 | **$0.0050** | $0.0099 |
| `gpt-5.4-nano` | 한 장, original | 6,843 | $0.0014 | $0.0037 | **$0.0051** | $0.0102 |
| `gpt-4.1-mini` | 7조각 | 12,628 | $0.0051 | $0.0048 | **$0.0099** | $0.0197 |
| `gpt-5.4-mini` | 한 장, original | 6,843 | $0.0051 | $0.0135 | $0.0186 | $0.0373 |
| `gpt-4o-mini` | 7조각 | 180,607 | $0.0271 | $0.0018 | $0.0289 | $0.0578 |
| `gpt-5.1` | 7조각 | 6,510 | $0.0081 | $0.0300 | $0.0381 | $0.0763 |
| `gpt-4.1` | 7조각 | 7,455 | $0.0149 | $0.0240 | $0.0389 | $0.0778 |
| `gpt-4o` | 7조각 | 7,455 | $0.0186 | $0.0300 | $0.0486 | $0.0973 |
| `gpt-5.6-terra` | 한 장, auto | 6,843 | $0.0137 | $0.0360 | $0.0497 | $0.0994 |
| `gpt-5.4` | 한 장, original | 6,843 | $0.0171 | $0.0450 | $0.0621 | $0.1242 |
| 로컬 OCR 엔진 | - | - | - | - | $0 | $0 |

- 7조각 방식의 입력 토큰은 `7 × (조각의 이미지 토큰 + 300)`이다. 예: `gpt-4.1-mini`는 7 × (1,504 + 300) = 12,628.
- 비싼 모델에서는 이미지가 아니라 출력이 비용의 대부분이다. 읽은 글자를 그대로 받아쓰게 하면 출력 토큰이 많기 때문이다.

### 3.4 $5 안에서의 여유

읽기에 $3을 쓴다고 가정했다. 나머지 $2는 조건 추출과 비교, 평가자의 실행 몫으로 남겼다. 이 배분은 가정이고, 정하는 것은 사용자다.

| 모델 | 공고 2건을 한 번 읽는 비용 | $3으로 읽을 수 있는 횟수 |
| :- | -: | -: |
| `gpt-5.6-luna`, `gpt-5.4-nano` | 약 $0.010 | 약 300회 |
| `gpt-4.1-mini` | 약 $0.020 | 약 150회 |
| `gpt-5.4-mini` | 약 $0.037 | 약 80회 |
| `gpt-4o-mini` | 약 $0.058 | 약 50회 |
| `gpt-4.1`, `gpt-5.1` | 약 $0.077 | 약 39회 |
| `gpt-4o`, `gpt-5.6-terra` | 약 $0.098 | 약 30회 |
| `gpt-5.4` | 약 $0.124 | 약 24회 |

- 해석: 읽은 결과를 파일로 저장해 두고 같은 이미지를 다시 읽지 않으면, 어느 모델이든 예산 안에 들어온다. 읽기는 공고 하나에 한 번만 하면 되는 일이다. 저장하지 않고 실행할 때마다 다시 읽으면 비싼 모델은 30회 안팎에서 예산이 끝난다.
- 해석: 후보 모델을 서로 비교해 재는 일(8장)은 모델 5개 × 공고 2건 × 2회를 해도 합계가 $1을 넘지 않는다.

## 4. 알려진 성능과 약점

### 4.1 확인한 것

| 자료 | 내용 |
| :- | :- |
| FaithC4 논문 (2026, arXiv 2607.21617) | 한국어 문서 455쪽을 포함한 벤치마크에서 15개 시스템을 쟀다. 한국어 단어 오류율(WER, 낮을수록 좋다)은 Gemini-3-Flash 4.85%, GPT-5.4-mini 8.23%, PaddleOCR-VL-1.5 20.55%, Tesseract 40.10%다. docTR은 한국어를 지원하지 않아 재지 못했다. |
| 같은 논문 | 범용 VLM은 글자가 불완전할 때 그대로 옮기지 않고 그럴듯한 형태로 **바꿔 쓴다**. 한국어에서 글자를 흩뜨렸을 때 늘어난 오류율은 GPT-5.4-mini가 +3.1 ~ +5.1%p로 15개 중 가장 컸고, Tesseract는 +0.2 ~ +3.6%p였다. 4~6자의 짧은 단어가 최대 10%까지 바뀌었다. 논문은 글자 그대로의 전사가 필요한 일에는 전통 OCR이나 골라 낸 OCR 전용 VLM이 안전하다고 적었다. |
| KOCRBench 논문 (2025, arXiv 2510.02543) | 한국어 OCR 벤치마크에서 글자 오류율(CER)이 PaddleOCR 49.6%, Surya 60.9%였다. 저자들의 모델(KLOCR)은 2.34%다. 저자들이 만든 모델을 내세운 비교다. |
| 같은 논문 | OCR로 읽은 글자를 VLM의 지시문에 함께 넣으면 한국어 문서 질문 응답의 점수가 모든 모델에서 올랐다. 핵심 정보 추출에서 가장 많이 올랐다. |
| PaddleOCR 공식 문서 | `korean_PP-OCRv5_mobile_rec`의 한국어 평가셋(글자 이미지 5,007장) 정확도가 88.0%다. 이전 세대보다 65.0% 개선되었다고 적었다(%p인지 비율인지는 확인하지 못했다). 문서가 아니라 잘라 낸 글자 이미지의 인식 정확도다. |
| Tesseract 공식 문서 | 300 DPI 이상에서 가장 잘 읽는다. 4.x부터는 밝은 바탕에 어두운 글자를 전제로 한다. 바탕의 밝기가 고르지 않으면 내부 이진화가 최적이 아닐 수 있다. 표에는 알려진 문제가 있다. |
| OpenAI 공식 문서 | 한국어에서 성능이 최적이 아닐 수 있다. 작은 글자는 키워서 보내라. 회전된 글자를 잘못 읽을 수 있다. 정밀한 위치 파악에 약하다. 틀린 설명을 만들 수 있다. |
| KIE-HVQA 논문 (2025, arXiv 2506.20168) | 흐릿한 문서에서 모델이 보이는 글자가 아니라 언어 지식에 기대어 답을 지어낸다. |

### 4.2 해석

- 두 논문의 수치는 서로 다른 데이터에서 나왔으므로 직접 비교할 수 없다. FaithC4는 9pt 글자를 깨끗하게 렌더링한 합성 문서이고, 디자인된 공고 이미지가 아니다. 방향만 읽는다.
- 읽을 수 있는 방향은 이렇다. 한국어에서 Tesseract와 PaddleOCR 같은 전통 OCR은 글자를 많이 틀린다. 범용 VLM은 글자를 덜 틀리지만 틀리는 방식이 위험하다. 전통 OCR은 깨진 글자를 내놓아서 틀린 것이 눈에 띄고, VLM은 그럴듯한 다른 단어를 내놓아서 틀린 것이 눈에 띄지 않는다.
- 채용 공고에서 이 차이가 중요한 곳은 숫자와 고유 명사다. "경력 3년 이상"의 3, 자격증과 도구의 이름, 급여, 마감일이다. 문맥으로 추측할 수 없는 값이기 때문이다(추측).
- 디자인된 이미지(색 배경, 흰 글자, 장식 폰트, 작은 글자)에서의 한국어 성능을 직접 잰 공개 자료는 찾지 못했다. Tesseract는 공식 문서의 내용으로 보아 색 배경과 흰 글자에 약할 것이다(추측). 전처리(흑백 변환, 반전, 확대)로 완화할 수 있다.
- LLM이 긴 이미지에서 일부를 빠뜨린다는 것을 수치로 잰 공개 자료는 찾지 못했다. 사용자들의 경험 글에는 긴 이미지가 줄어들어 작은 글자가 사라졌다는 보고가 있고, 겹치게 잘라 보내면 나아졌다는 보고가 있다. 3.2의 계산과 맞는 이야기다.

## 5. 표와 배치의 보존

"무엇이 어느 항목 아래에 있는지"가 보존되어야 자격요건과 우대사항을 구분할 수 있다.

| 방법 | 항목 구분(제목과 그 아래 내용) | 표의 행·열 | 좌표 |
| :- | :- | :- | :- |
| Tesseract | 블록, 문단, 줄의 순서만 준다. 어느 줄이 제목인지는 주지 않는다. | 보존하지 않는다. | 단어마다 상자 |
| PaddleOCR (PP-OCRv5) | 줄의 목록만 준다. | 보존하지 않는다. | 줄마다 다각형 |
| PaddleOCR (PP-StructureV3) | 제목, 본문, 표 같은 영역 종류와 읽기 순서를 준다. | 셀 좌표를 준다. | 영역과 셀마다 상자 |
| Surya | 배치 영역과 읽기 순서를 준다. | 행·열을 HTML로 준다. | 블록마다 상자 |
| 클로바 OCR (참고) | 줄바꿈 여부만 준다. | 셀의 행·열 번호와 병합 정보를 준다. | 글자마다 다각형 |
| OpenAI 비전 모델 | 마크다운 제목과 목록으로 받아쓰게 할 수 있다. | 마크다운 표로 받아쓰게 할 수 있다. | 없다 |

- 해석: 좌표가 있으면 근거의 출처를 "공고 이미지의 이 자리"로 가리킬 수 있다(`problem.md` 1.2의 6번). 좌표를 주는 것은 로컬 OCR 엔진뿐이다.
- 해석: 로컬 OCR 엔진이 표의 구조를 주지 않아도, 줄마다 좌표가 있으면 y좌표로 줄을 묶고 x좌표로 열을 나누어 표를 어느 정도 되살릴 수 있다. 얼마나 되는지는 재야 안다.
- 해석: LLM의 표·배치 보존은 지시문에 달려 있고 보장되지 않는다. 표의 칸을 밀려 쓰는 실패가 있을 수 있다(추측).
- 추천 후보 3번(함께 쓰기)에서는 LLM이 읽은 구절을 로컬 OCR 엔진의 줄과 맞추어 좌표를 붙일 수 있다. 맞는 줄이 없는 구절은 LLM이 지어냈을 가능성이 있다는 신호가 된다(해석).

## 6. 읽기가 틀릴 수 있음을 다루는 방법

| 접근 | 내용 | 한계 |
| :- | :- | :- |
| 신뢰도 점수 | 로컬 OCR 엔진은 단어나 줄마다 점수를 준다. 낮은 곳을 "확인 필요"로 표시한다. | 점수가 실제 정확도와 얼마나 맞는지는 확인하지 못했다. LLM은 글자별 점수를 주지 않는다. |
| 두 방법의 교차 확인 | 로컬 OCR 엔진과 LLM의 결과를 비교해 다른 곳을 표시한다. | 둘 다 같은 식으로 틀리면 잡지 못한다. 줄바꿈과 띄어쓰기의 차이를 걸러야 한다. |
| 같은 모델로 두 번 읽기 | 겹친 구간(150픽셀)이 양쪽 조각에서 같게 읽혔는지 본다. 조각의 끝 문장이 다음 조각의 첫 문장과 이어지는지 본다. | 빠뜨림은 잡을 수 있으나 바꿔 쓰기는 잡기 어렵다. |
| 빠뜨림 검사 | 로컬 OCR 엔진이 검출한 글자 상자의 수나 글자 수와, LLM이 낸 글자 수를 조각마다 비교한다. | 기준값을 정해야 한다. |
| 형식 검사 | 숫자, 날짜, 기간을 정규식으로 뽑아 두 결과에서 같은지 본다. 조건 추출이 낸 값이 읽은 글자 안에 실제로 있는지 본다. | 결정론적으로 할 수 있는 검사다. 값이 맞는지가 아니라 근거가 있는지만 본다. |
| 사람이 확인 | 채용 담당자가 추출된 조건을 원본 이미지 옆에서 보고 고친다. | `problem.md` 1.1의 4번, 5번과 같은 흐름이다. 자기 공고이므로 담당자가 정답을 안다. |

- 해석: 이 서비스는 사람이 조건을 확인하는 단계를 이미 가지고 있다. 그래서 읽기의 목표는 "틀리지 않는다"가 아니라 "틀렸을 만한 곳을 사람에게 가리킨다"로 잡을 수 있다. 정하는 것은 사용자다.

## 7. 읽기의 자리에 대한 판단 재료

`law/law.md` 4장은 읽기의 자리를 법이 아니라 기술의 문제로 보았다. 이 장은 그 기술 쪽 재료다.

| 방법 | 고객사의 브라우저 | 고객사의 PC(설치형) | 서비스 제공사의 서버 |
| :- | :- | :- | :- |
| Tesseract | 된다. tesseract.js가 WebAssembly로 돈다(Apache-2.0). 언어 데이터는 처음 쓸 때 내려받아 캐시한다. | 된다. | 된다. |
| PaddleOCR (PP-OCRv5) | 공식 브라우저 SDK(`@paddleocr/paddleocr-js`)가 있다. 문서의 예는 중국어뿐이라 **한국어 모델이 되는지 확인하지 못했다.** 사용자 모델을 넣는 길은 있다. | 된다. | 된다. |
| PP-StructureV3, Surya | 확인하지 못했다. 모델이 커서 어려울 것이다(추측). | 된다. 무겁다. | 된다. |
| OpenAI 비전 모델 | API 키를 브라우저에 둘 수 없다. | 고객사가 자기 키를 넣어야 한다. | 된다. |
| 클라우드 OCR (참고) | 키를 브라우저에 둘 수 없다. | 고객사가 자기 키를 넣어야 한다. | 된다. |

판단 재료는 네 가지다.

- **LLM으로 읽으면 이미지가 서버를 거친다.** 고객사 쪽에서 OpenAI를 부르려면 키가 필요하다. 서비스 제공사의 키를 쓰려면 서비스 제공사의 서버가 호출을 대신해야 하고, 그러면 이미지가 서버로 넘어온다. 서버가 이미지를 저장하지 않고 거쳐 보내기만 할 수는 있다. 고객사가 자기 키를 넣는 방식은 B2B 서비스로서 부담이 크다(해석).
- **고객사 쪽에서 읽으려면 로컬 OCR 엔진이어야 한다.** 그 경우 읽기의 품질이 로컬 OCR 엔진의 한국어 성능에 묶인다. 4장의 자료로는 이 성능이 낮을 수 있다.
- **고객사 쪽에서 읽으면 서버가 원본을 볼 수 없다.** 교차 확인(6장)과 좌표로 출처를 가리키는 일은 원본 이미지가 있어야 한다. 사람이 확인하는 화면은 고객사의 브라우저에서 원본을 보여 주면 되므로 서버에 원본이 없어도 된다(해석).
- **과제의 실행에서는 경계가 컨테이너로 표현된다.** 평가자는 Docker Compose 하나로 실행한다. 고객사 쪽(수집과 읽기)과 서버(조건 추출 이후)를 서로 다른 서비스로 나누어 경계를 보일 수 있다. 이것은 09 단계에서 정할 일이다.

선택지를 줄이면 이렇다.

| 선택지 | 읽기의 자리 | 서버가 받는 것 | 읽기의 품질 | 좌표 |
| :- | :- | :- | :- | :- |
| 가. 로컬 OCR 엔진만 | 고객사 쪽 | 글자와 좌표 | 로컬 OCR 엔진에 묶인다. 조건 추출의 LLM이 깨진 글자를 얼마나 견디는지에 달렸다. | 있다 |
| 나. LLM만 | 서버(또는 서버를 거침) | 이미지 | LLM에 묶인다. 바꿔 쓰기를 잡을 수단이 약하다. | 없다 |
| 다. 고객사 쪽에서 로컬 OCR 엔진, 서버에서 LLM이 이미지를 다시 읽어 교차 확인 | 양쪽 | 글자, 좌표, 이미지 | 가장 높을 것이다(추측). | 있다 |
| 라. 고객사 쪽에서 로컬 OCR 엔진, 서버의 LLM은 글자만 받아 교정과 조건 추출 | 고객사 쪽 | 글자와 좌표 | LLM이 깨진 글자를 문맥으로 고친다. 고치면서 바꿔 쓸 위험이 있다. | 있다 |

- 해석: "가"와 "라"는 `law.md`가 본 방향(이미지가 서비스 제공사로 넘어오지 않는다)을 지킨다. "나"와 "다"는 지키지 못한다. 어느 쪽을 고를지는 로컬 OCR 엔진이 실제 공고에서 쓸 만한지에 달려 있고, 그것은 8장으로 잰다.

## 8. 직접 잴 때의 계획

공고 이미지를 고른 뒤 사용자가 허락하면 한다. 유료 호출이 들어간다.

### 8.1 후보

| 후보 | 구성 | 재는 이유 |
| :- | :- | :- |
| A | PaddleOCR(PP-OCRv5 한국어)로 읽는다. 전처리 없음과 있음 두 가지. | 고객사 쪽에서 읽는 선택지(가, 라)가 성립하는지 본다. |
| B | OpenAI 비전 모델이 읽는다. 싼 모델 하나(`gpt-5.4-nano` 또는 `gpt-5.6-luna`)와 한 단계 위 모델 하나(`gpt-4.1-mini` 또는 `gpt-5.4-mini`). 자른 것과 자르지 않은 것 두 가지. | 모델의 등급과 자르기가 정확도에 주는 영향을 본다. |
| C | Tesseract(`kor+eng`)로 읽는다. | 브라우저에서 확실히 도는 기준선이다. |

### 8.2 정답과 채점

- 정답: 고른 공고 2건의 이미지를 사람이 직접 받아써서 정답 글자를 만든다. 자격요건, 우대사항 같은 항목 구분과 표의 행·열도 함께 적는다.
- 정답을 만들 때 OCR이나 LLM의 결과를 초안으로 쓰지 않는다. 초안의 오류가 정답에 남기 때문이다.

| 비교 기준 | 어떻게 채점하는가 |
| :- | :- |
| 글자 정확도 | 띄어쓰기와 줄바꿈을 정규화한 뒤 글자 오류율(편집 거리 ÷ 정답 글자 수)을 계산한다. |
| 핵심 값의 정확도 | 정답에서 숫자, 기간, 날짜, 자격증·도구 이름을 미리 표시해 두고, 그 값이 결과에 그대로 있는지를 센다. 글자 오류율보다 이것을 더 무겁게 본다. |
| 지어냄과 빠뜨림 | 결과에만 있는 구절과 정답에만 있는 구절을 따로 센다. 글자 오류율 하나로 합치지 않는다. |
| 표·배치 보존 | 정답의 각 조건이 올바른 항목(자격요건/우대사항 등) 아래에 있는지, 표의 값이 올바른 행·열에 있는지를 조건 단위로 센다. |
| 반복 안정성 | LLM 후보는 같은 입력으로 3번 실행해 결과가 같은지 본다. |
| 비용 | API 응답의 실제 토큰 사용량을 기록한다. 3장의 계산과 비교한다. 추론 토큰이 얼마나 나오는지도 기록한다. |
| 시간과 설치 부담 | 로컬 후보는 Docker 이미지 크기와 이미지 한 장의 CPU 처리 시간을 잰다. |
| 고객사 쪽 실행 가능성 | 7장의 표로 판단한다. PaddleOCR의 브라우저 SDK가 한국어 모델로 도는지는 따로 확인한다. |

### 8.3 예상 비용

3장의 가정으로 LLM 모델 2개 × (자른 것, 자르지 않은 것) × 공고 2건 × 3회를 하면 약 $0.3 이하다. 실제 이미지의 크기를 잰 뒤 다시 계산하고, 호출 전에 사용자에게 금액을 알린다.

## 9. 깨질 수 있는 지점 (테스트 케이스 후보)

| 지점 | 무엇이 깨지는가 |
| :- | :- |
| 세로 6000픽셀을 넘는 이미지 | 자르지 않으면 줄어들어 글자가 뭉개진다. `gpt-5.4` 계열의 `original`도 6000픽셀을 넘으면 줄인다. |
| 자른 경계에 걸린 줄 | 한 줄이 두 조각으로 나뉘어 반쪽 글자가 된다. 겹침 구간의 글자가 두 번 나온다. |
| 표의 가운데에서 자른 경우 | 아래 조각에 표의 머리 행이 없어 열의 뜻을 잃는다. |
| 색 배경 위의 흰 글자, 사진 위의 글자 | 로컬 OCR 엔진이 글자를 검출하지 못한다. |
| 작은 글자(각주, 유의사항) | 로컬 OCR 엔진과 LLM 모두 틀리거나 빠뜨린다. |
| 숫자와 단위 | "3년"이 "8년"으로, "~"와 "-"가 바뀐다. LLM은 그럴듯한 숫자로 바꿔 쓴다. |
| 영어와 한글이 섞인 이름 | 도구와 자격증의 이름이 비슷한 다른 이름으로 바뀐다. |
| 두 단 배치 | 왼쪽 단과 오른쪽 단의 줄이 섞여 읽힌다. |
| 자격요건과 우대사항이 나란히 놓인 표 | 우대사항의 항목이 자격요건으로 들어간다. 뒤의 점수에 바로 영향을 준다. |
| 병합된 칸이 있는 표 | 값이 한 칸씩 밀린다. |
| 아이콘과 장식 글자 | 장식을 글자로 읽거나 체크 표시를 글자로 읽는다. |
| 이미지가 여러 장인 공고 | 장의 순서가 바뀌거나 한 장이 빠진다. |
| 본문이 이미지가 아니라 글자인 공고 | 읽기 단계가 필요 없다. 과제는 이미지 공고를 요구했으므로 공고를 고를 때 걸러야 한다. |
| 같은 입력을 다시 실행 | LLM의 결과가 실행마다 달라진다. 읽은 결과를 저장하지 않으면 점수가 흔들린다. |

## 10. 확인하지 못한 것

- 3장의 비용 계산은 가정한 크기(900×6,000픽셀)로 한 것이다. 실제 후보 8건은 한 장짜리 660×750픽셀부터 세 장을 합쳐 860×20,323픽셀까지다(`posting/posting.md`). 실제 크기로 다시 계산하지 않았다.
- 한글 한 글자가 출력에서 몇 토큰인지와, `gpt-5` 계열의 추론 토큰이 받아쓰기에서 얼마나 나오는지. 출력 비용의 가정(3,000토큰, 추론 0)에 영향을 준다.
- `gpt-6-luna`, `gpt-6-sol`, `gpt-6.1-sol`의 이미지 토큰 계산 규칙. 공식 문서의 표에 없었다.
- 과제에서 받은 OpenAI 키로 어느 모델을 부를 수 있는지. `.env`를 읽지 않았고 API를 호출하지 않았다.
- 디자인된 한국어 이미지(채용 공고, 포스터)에서 각 방법의 정확도. 공개된 자료를 찾지 못했다.
- 기본형 PaddleOCR(PP-OCRv5)과 EasyOCR의 한국어 문서 정확도를 OpenAI 모델과 같은 데이터에서 잰 자료. FaithC4는 PaddleOCR-VL만 쟀다.
- LLM이 긴 이미지에서 일부를 빠뜨리는 비율. 경험 글만 있다.
- 네이버 클로바 OCR의 공식 가격. 가격 페이지의 내용을 읽지 못했다.
- Tesseract의 한국어 학습 데이터 크기, PaddleOCR과 Tesseract의 Docker 이미지 크기, 이미지 한 장 전체의 CPU 처리 시간.
- PaddleOCR의 CPU용 패키지가 ARM(Apple Silicon의 Docker)에서 설치되는지. 평가자의 PC가 Mac일 수 있다.
- PaddleOCR의 브라우저 SDK가 한국어 인식 모델을 지원하는지.
- tesseract.js의 한국어 정확도. 재어 본 자료를 찾지 못했다.
- 로컬 OCR 엔진의 신뢰도 점수가 실제 정확도와 얼마나 맞는지.
- 2023년의 국내 학술대회 논문(Tesseract와 PaddleOCR의 한국어 비교). 원문에 접속하지 못해 인용하지 않았다.

### 11.3 눈으로 본 것

PaddleOCR의 결과에서 확인한 것이다.

- **띄어쓰기를 잃는다.** 작은 글자에서는 한 줄 전체가 붙어서 읽혔다. 채점에서는 띄어쓰기를 지웠으므로 오류율에 잡히지 않았다. 인용이 원문에 있는지를 대조할 때 띄어쓰기를 지우고 대조해야 한다.
- **신뢰도가 틀린 글자를 가리키지 못한다.** 틀린 세 줄의 신뢰도는 0.93~0.95로, 맞게 읽은 줄과 같은 범위다. 신뢰도가 0.8보다 낮은 줄은 940줄 가운데 57줄이고, 대부분 사진 속의 글자, 도식의 아이콘, 장식 글자, 잘린 경계의 줄이었다. 신뢰도는 "뜻 없는 글자"를 거르는 데는 쓸 수 있고, "조건 안의 틀린 글자"를 찾는 데는 쓸 수 없다.
- **읽는 순서가 섞인다.** 왼쪽에 칸 이름이 있고 오른쪽에 내용이 있는 배치에서, 칸 이름("자격요건", "(필수)")이 내용의 줄 사이에 끼어 나왔다. 표에서는 행의 제목이 칸의 내용 사이에 끼어 나왔다. 줄마다 좌표가 있으므로 좌표로 다시 묶을 수는 있다.
- **두 줄에 걸친 조건은 두 줄로 나온다.** 한 조건인지 두 조건인지는 읽은 결과만으로는 알 수 없다.
- **표의 칸 경계는 나오지 않는다.** 한 칸에 필수와 우대가 함께 있는 표에서 "[우대사항]"이라는 줄은 읽혔다. 칸의 경계는 좌표로 짐작해야 한다.
- **잘린 경계의 줄을 틀리게 읽는다.** 조각의 경계에 걸린 제목과 본문 한 줄이 엉뚱한 글자로 읽혔다. 겹쳐서 잘라야 한다.
- **아주 작은 글자를 틀린다.** 660×750픽셀 이미지의 주소 줄(웹 주소와 메일 주소)은 틀리게 읽혔다. 같은 이미지의 조건 줄은 위의 한 줄을 빼고 맞게 읽혔다.
- **뜻 없는 글자가 섞인다.** 배경의 장식 글자, 건물의 간판, 제품의 상표가 읽혔다.
- **사진 위의 흰 글자와 색이 바뀌는 배경 위의 표는 읽혔다.** 9장에서 걱정한 것보다 나았다.

### 11.4 해석

- 이 8건에서는 PaddleOCR의 글자 정확도가 조건을 뽑기에 충분하다. 4.1의 공개 자료(로컬 OCR 엔진이 한국어 글자를 더 많이 틀린다)보다 나은 결과다. 공고 이미지는 사진으로 찍은 문서가 아니라 디자인 도구에서 내보낸 또렷한 그림이기 때문으로 보인다. 추측이다.
- EasyOCR은 조건 줄의 절반 이상에서 글자를 틀렸다. 후보에서 빼도 된다.
- 로컬 OCR 엔진의 약점은 글자가 아니라 구조다. 읽는 순서, 칸의 경계, 줄이 넘어간 조건을 잃는다. 이것은 뒤의 조건 추출이 받아야 하는 부담이다. 조건 추출은 LLM이 하기로 했으므로(`CHECKLIST.md`의 `08_algorithm`), 글자와 좌표를 함께 넘기면 LLM이 구조를 다시 세울 수 있는지가 남은 질문이다. 재지 않았다.
- 틀린 글자 가운데 하나는 도구의 이름이고 하나는 회계 기준의 이름이다. 둘 다 "갖고 있는가"를 이름으로 대조하는 조건에 들어가는 글자다. 글자 오류율이 낮아도 이런 값이 틀리면 판정이 틀린다.
- 비용 쪽의 차이는 작다. 3.3의 계산으로 OpenAI 비전 모델은 공고 한 건에 약 $0.005~$0.06이다. 로컬 OCR 엔진은 $0이지만 설치할 것이 수백 MB이고 공고 한 건을 읽는 데 CPU로 5초에서 90초가 든다. 두 방법을 가르는 것은 비용보다 설치의 무게, 결정론적인가, 구조를 보존하는가다.

### 11.5 재지 못한 것

- OpenAI 비전 모델의 정확도, 바꿔 쓰기, 빠뜨리기. 키를 쓰지 않았다. 그래서 두 방법 가운데 어느 쪽이 나은지는 이 결과로 말할 수 없다.
- Docker(리눅스) 안에서 PaddleOCR이 설치되고 도는지, Docker 이미지의 크기. macOS에 직접 설치해서 쟀다.
- PaddleOCR의 모바일용(가벼운) 모델의 정확도와 시간.
- 겹쳐서 자른 경우와 자르지 않은 경우의 차이.
- 조건 줄 밖의 글자(회사 소개, 복리후생, 인재상)의 정확도.
- 글자와 좌표를 넘겼을 때 LLM이 표와 칸을 다시 세울 수 있는지.

### 11.6 LLM의 읽기와 견주어 본 것 (에이전트가 직접 읽음)

2026-10-11에 사용자의 요청으로, 에이전트(Claude)가 같은 이미지를 직접 받아쓰고 PaddleOCR의 결과와 견주었다. OpenAI 키는 쓰지 않았다.

이 비교가 말해 주는 범위는 좁다.

- 읽은 것은 Claude다. 프로그램이 쓸 OpenAI의 모델이 아니다. "LLM이 이미지를 읽으면 이 정도가 된다"의 참고일 뿐이고, OpenAI의 싼 모델이 같은 결과를 낸다는 뜻이 아니다.
- 11.1의 정답도 에이전트가 만들었다. 그래서 정답에 대고 채점하지 않고, 두 결과가 어긋나는 자리를 찾아 그 자리를 4배로 확대해서 어느 쪽이 맞는지 보았다. 두 쪽이 똑같이 틀린 글자는 이 방법으로 찾을 수 없다. 어느 쪽이 맞는지를 가린 것도 에이전트다.

대상은 11.1의 8조각 전체다. 조건 줄만이 아니라 조각에 있는 글자 전부(띄어쓰기를 빼고 약 2,750자)다.

| | 에이전트(Claude)가 읽은 것 | PaddleOCR |
| :- | :- | :- |
| 확대해서 보았을 때 틀린 글자 | 찾지 못했다 | 13자 (약 0.5%) |
| 틀린 자리 | | 직무→질무, 도구 이름의 첫 글자를 빠뜨림, 회계 기준 이름의 글자 하나와 닫는 괄호를 빠뜨림, 웹 주소 5자, 메일 주소 3자, 그리스 글자를 영어 글자로 읽음 |
| 문장 끝의 마침표 | 읽었다 | 다섯 줄에서 빠뜨렸다 |
| 뜻 없는 글자 | 없다 | 일곱 군데 (도식의 아이콘, 로고, 사진) |
| 띄어쓰기 | 이미지와 같다 | 작은 글자에서 잃는다 |
| 칸 이름과 내용의 묶음 | 칸 이름 아래에 내용을 묶어서 읽었다 | 좌표 순서로 나와서 칸 이름이 내용 사이에 낀다 |
| 조각의 경계에 걸린 줄 | 앞 조각을 함께 보았기 때문에 읽었다. 조각 하나만으로는 읽을 수 없는 줄이다 | 틀리게 읽었다 |

- 조건 줄에서 어긋난 것은 11.2의 세 줄뿐이다. 세 줄 모두 확대해서 보니 PaddleOCR이 틀렸다.
- PaddleOCR이 틀린 13자 가운데 8자는 660×750픽셀 이미지의 웹 주소와 메일 주소다. 조건이 아닌 글자다.
- 긴 이미지를 자르지 않고 줄여서 볼 때는 에이전트도 읽지 못했다. 860×7,048픽셀 이미지를 높이 1,800픽셀로 줄인 그림에서는 큰 제목만 읽혔고 본문은 읽기 어려웠다. LLM으로 읽을 때도 잘라서 보내야 한다(3.2).

해석이다.

- 글자만 보면 두 방법의 차이는 작다. 조건 줄에서 PaddleOCR이 더 틀린 것은 64줄 가운데 3줄이다.
- 차이가 나는 곳은 구조다. LLM의 읽기는 띄어쓰기, 칸 이름과 내용의 묶음을 그대로 준다. PaddleOCR은 주지 않는다.
- LLM의 읽기에서 걱정한 바꿔 쓰기와 빠뜨리기는 이 8조각에서는 찾지 못했다. 다만 이것은 Claude가 한 번 읽은 결과다. 반복해서 읽었을 때 같은지, OpenAI의 싼 모델도 그런지는 알 수 없다.

### 11.7 엔진 여섯 가지를 공고 8건으로 견준 것

2026-10-11에 사용자의 요청으로 엔진을 늘려 공고별로 견주었다. OpenAI 키는 쓰지 않았다.

- 기준: 11.6에서 에이전트(Claude)가 받아쓰고 어긋난 자리를 확대해서 확인한 글자다. 공고 8건에서 조건이 있는 조각 하나씩, 띄어쓰기와 기호를 빼고 2,688자다. 조각의 경계에 걸린 줄 하나와 배경의 장식 글자 하나는 뺐다.
- 그래서 Claude의 읽기는 이 표에서 채점 대상이 아니라 기준이다. Claude의 읽기에서 틀린 글자는 11.6의 방법으로 찾지 못했다.
- 채점: 기준의 줄마다, 엔진이 읽은 전체 글자 안에서 가장 가깝게 들어 있는 자리의 편집 거리를 셌다. 읽는 순서가 섞여도 줄 안의 글자가 맞으면 맞은 것으로 센다.

공고별 글자 오류율(%)이다. 띄어쓰기를 빼고 센 것이다.

| 엔진 | 영업 | 영업 지원 | 회계 | 고객상담 | 마케팅 디자인 | 마케팅 | 물류 (55073054) | 물류 (55136328) | 전체 |

- **모든 엔진이 회계 공고에서 가장 많이 틀렸다.** 660×750픽셀 한 장에 글자가 작게 들어 있는 공고다. 틀린 글자는 대부분 웹 주소와 메일 주소다.
- **Tesseract는 공고의 디자인에 크게 흔들린다.** 회색 배경에 회색 글자인 마케팅 공고에서 80%를 틀렸고, 흰 배경에 검은 글자인 공고에서는 3.9%였다.
- **PaddleOCR은 한국어 인식 모델을 지정하지 않으면 한글을 읽지 못한다.** 검출 모델의 이름을 직접 주었더니 언어 설정이 무시되어 다른 인식 모델(PP-OCRv6)이 쓰였고, 84%를 틀렸다. 설정 한 줄로 결과가 뒤집히는 자리다.
- **가벼운 검출 모델이 서버용보다 빠르고 이 8건에서는 더 맞았다.** 차이는 5자다. 표본이 작아 우열이라고 하기 어렵다.
- **띄어쓰기는 macOS 내장 OCR만 지켰다.** PaddleOCR은 글자는 가장 잘 맞지만 띄어쓰기를 넣고 세면 8%대로 오른다.

해석이다.

- 후보로 남는 로컬 엔진은 PaddleOCR 하나다. macOS 내장 OCR은 정확하지만 평가자의 Docker 안에서 돌지 않는다. EasyOCR과 Tesseract는 조건 줄의 절반가량에서 글자를 틀린다.
- LLM의 읽기(Claude 기준)와 PaddleOCR의 글자 차이는 2,688자 가운데 9~14자다. 글자로는 갈리지 않는다. 갈리는 것은 띄어쓰기와 구조, 설치의 무게, 결정론적인가다(11.6).

### 11.9 정답이 있는 공개 데이터셋으로 잰 것

2026-10-11에 사용자의 지적으로 더했다. 11.6과 11.7은 정답을 에이전트가 만들었다. 그래서 정답이 붙어 있는 공개 데이터셋으로 다시 쟀다.

| 항목 | 내용 |
| :- | :- |
| 데이터셋 | [CC-OCR](https://huggingface.co/datasets/wulipc/CC-OCR)의 다국어 OCR 가운데 한국어 150장(`multi_lan_ocr/Korean/Korean_150.tsv`). MIT 라이선스다. 로그인 없이 받을 수 있다. |
| 이미지의 성격 | 거리의 간판, 현수막, 안내판을 찍은 사진이 대부분이다. 문서를 찍은 사진과 발표 자료가 몇 장 있다. 채용 공고처럼 디자인 도구에서 내보낸 그림이 아니다. |
| 표본 | 정답의 길이 순으로 줄을 세워 여섯 장마다 한 장씩 25장. 정답의 길이는 7자에서 847자다. |
| 엔진 | 11.7의 다섯 가지. 원본 크기의 사진을 그대로 넣었다. |
| Claude | 에이전트가 긴 변을 1,568픽셀로 줄인 사진을 보고 받아썼다. 받아쓰기 전에 정답을 보지 않았다. |
| 채점 | 정답은 낱말을 나열한 것이고 순서가 정해져 있지 않다. 그래서 순서를 보지 않고, 글자와 단어를 각각 세어 겹치는 수로 재현율(정답 가운데 읽은 것), 정밀도(읽은 것 가운데 맞은 것), F1을 계산했다. 기호와 띄어쓰기는 뺐다. |

| 읽은 것 | 글자 재현율 | 글자 정밀도 | 글자 F1 | 단어 재현율 | 단어 정밀도 | 단어 F1 | 장당 시간 |
| :- | :- | :- | :- | :- | :- | :- | :- |
| Claude | 89.3 | 98.0 | 93.5 | 76.8 | 88.1 | 82.1 | 재지 않았다 |
| macOS 내장 OCR (Vision) | 83.7 | 95.9 | 89.4 | 75.4 | 85.3 | 80.0 | 0.2초 |
| PaddleOCR (서버용 검출 모델) | 67.3 | 81.3 | 73.6 | 43.3 | 56.4 | 49.0 | 33.1초 |
| PaddleOCR (가벼운 검출 모델) | 60.1 | 81.2 | 69.1 | 40.2 | 54.1 | 46.2 | 2.7초 |
| EasyOCR | 50.5 | 73.2 | 59.7 | 28.1 | 34.1 | 30.8 | 3.0초 |
| Tesseract | 28.4 | 70.6 | 40.5 | 19.0 | 47.1 | 27.0 | 0.6초 |

확인한 것이다.

- **사진에서는 순위와 격차가 달라진다.** 공고 이미지에서는 PaddleOCR과 Claude의 글자 차이가 0.5% 안쪽이었는데, 사진에서는 글자 F1이 20점 넘게 벌어졌다.
- **PaddleOCR이 크게 놓친 사진이 있다.** 글자가 화면을 가득 채운 큰 간판 석 장에서 한 글자도 맞히지 못했다. 옆으로 돌아간 문서 사진(정답 847자)에서는 글자 F1이 28이었고, Claude는 99였다. 방향 보정을 끈 설정으로 쟀다.
- **Claude가 틀린 곳은 작은 글자가 많은 사진이다.** 시장 골목 사진(정답 257자)에서는 글자 F1이 33이었다. 줄인 사진에서 읽을 수 없는 글자를 적지 않았기 때문이다.
- **서버용 검출 모델은 큰 사진에서 매우 느리다.** 장당 평균 33초다. 가벼운 모델은 2.7초다.
- **정답에 한계가 있다.** 읽기 어려운 글자가 `*`로 가려져 있고, 작은 글자가 빠진 사진이 있다. 정밀도는 그만큼 낮게 나온다.

해석이다.

- 이 데이터셋의 결과를 채용 공고에 그대로 옮길 수 없다. 사진은 기울고 흐리고 글자 크기가 제각각이다. 공고 이미지는 또렷하고 반듯하다. PaddleOCR은 공고 이미지에서 99.6%였다.
- 두 결과를 함께 보면 이렇게 읽힌다. 이미지가 또렷할 때는 로컬 OCR 엔진과 LLM의 차이가 작고, 이미지가 나쁠수록 LLM이 앞선다. 고객사가 공고를 사진으로 찍어 넣는 경우까지 다뤄야 한다면 LLM 쪽이 튼튼하다. 사람인의 본문 이미지만 다룬다면 차이가 작다.
- 공고와 비슷한 이미지(디자인된 한국어 문서)에 정답이 붙은 공개 데이터셋은 찾지 못했다. 그래서 정답이 있는 데이터는 공고와 성격이 다르고, 공고와 같은 데이터는 정답을 에이전트가 만들었다. 두 한계는 그대로 남는다.
- OpenAI의 모델은 여전히 재지 못했다. Claude의 결과가 OpenAI의 싼 모델에도 맞는지는 알 수 없다.

### 11.10 더 나은 로컬 OCR이 있는가

2026-10-11에 사용자의 질문으로 찾아본 것이다.

- 확인: 문서 분석 벤치마크(OmniDocBench)의 위쪽은 글자 인식 엔진이 아니라 문서를 통째로 읽는 작은 비전-언어 모델이다. 2026년 4월의 한 집계에서 GLM-OCR, PaddleOCR-VL-1.5(파라미터 약 9억 개), MinerU 2.5가 앞에 있다(검색 요약으로 확인). 이 벤치마크는 중국어와 영어 문서다. 한국어 수치는 찾지 못했다.
- 확인: 일반적인 안내 글들은 여러 언어의 문서에는 PaddleOCR을 먼저 써 보라고 권한다. 배치가 복잡한 문서에는 Surya를, 가벼운 설치에는 RapidOCR(PaddleOCR의 모델을 ONNX로 돌림)을 든다(검색 요약으로 확인). 한국어를 CPU에서 견준 자료는 찾지 못했다.
- 직접 해 본 것: PaddleOCR에 들어 있는 문서 분석 파이프라인(PP-StructureV3)을 공고 조각 네 장에 돌렸다. 제목과 문단을 마크다운으로 나누어 주었다. 그러나 작은 표 하나는 칸의 순서가 뒤집히고 뜻 없는 글자가 섞여 나왔다. 모델을 처음 올리는 데 91초가 걸렸고 모델이 약 1GB였다. 조각당 8~23초였다. 이 과제의 이미지에서는 글자만 읽는 것보다 낫다고 하기 어려웠다.
- 해석: PaddleOCR보다 구조를 잘 읽는 로컬 방법은 있다. 다만 모두 작은 비전-언어 모델이고, CPU에서 느리거나 GPU가 필요하고, 설치가 더 무겁다. 구조를 읽는 일을 LLM에게 맡길 것이라면, 로컬에 작은 모델을 올리는 것보다 이미 쓰는 LLM 호출에 맡기는 쪽이 단순하다.
- 재지 않은 것: PaddleOCR-VL, Surya, RapidOCR, docTR.

### 11.11 OpenAI의 모델로 잰 것

2026-10-11에 사용자가 키를 쓰도록 허락해서 쟀다. 쓴 비용은 모두 합쳐 약 $0.06이다(API 응답의 토큰 사용량에 가격표를 곱한 값).

| 항목 | 내용 |
| :- | :- |
| 모델 | `gpt-5.6-luna`(추론을 하는 가장 싼 축, 추론 강도 낮음)와 `gpt-4.1-mini`(추론을 하지 않음, 온도 0) |
| 이미지 | 11.7의 공고 8조각. `gpt-5.6-luna`는 11.9의 데이터셋 25장(긴 변 1,568픽셀로 줄임)도 읽었다. |
| 지시 | 보이는 그대로 모두 받아쓰고, 고치거나 요약하지 말고, 읽을 수 없는 글자는 쓰지 말라고 했다. |
| 반복 | 공고 8조각은 모델마다 같은 입력으로 두 번 읽었다. |

공고 8조각의 결과다. 기준은 11.7과 같다.

| | `gpt-4.1-mini` | `gpt-5.6-luna` | PaddleOCR (가벼운 검출 모델) |
| :- | :- | :- | :- |
| 한 글자도 틀리지 않은 조건 줄 (64줄) | 64 | 64 (첫 번째 실행) | 63 |
| 글자 오류율 (2,688자) | 0.97% (26자) | 0.37% (10자) | 0.33% (9자) |
| 단어 정확도 (띄어쓰기까지 맞아야 함) | 99.4% | 99.1% | 68.3% |
| 숫자나 영문이 든 단어 105개 | 96.2% | 99.0% | 94.3% |
| 두 번 읽어 결과가 같은 조각 (8조각) | 7 | 1 | 같다 (결정론적) |
| 조각당 시간 | 2.8초 | 6.9초 | 2.8초 |
| 8조각을 한 번 읽는 비용 | $0.0095 | $0.0083 | $0 |

틀린 자리의 종류가 모델마다 다르다.

- **`gpt-4.1-mini`는 빠뜨린다.** 틀린 26자 가운데 25자는 로고의 영문 글자(회사 이름의 영문 표기)와 배경의 장식 글자를 적지 않은 것이다. 본문에서 틀린 것은 담당 업무의 한 글자뿐이다. 두 번째 실행에서 달라진 것도 로고 글자 하나를 적었느냐였다.
- **`gpt-5.6-luna`는 그럴듯하게 바꿔 쓴다.** 회사 이름의 한 글자를 다른 글자로, "이후"를 "중인"으로, "모십니다"를 "모집합니다"로, 사업의 이름을 다른 낱말로 바꿔 썼다. 로고의 영문 이름도 비슷한 다른 낱말로 적었다. 조각의 경계에 잘린 줄은 없는 낱말로 채웠다. 모두 조건 밖의 글자였다.
- **`gpt-5.6-luna`는 읽을 때마다 달라진다.** 두 번째 실행에서는 8조각 가운데 7조각이 첫 번째와 달랐다. 바꿔 쓴 자리가 실행마다 바뀌었고, 두 번째 실행에서는 자격요건의 학력 조건 한 글자가 다른 글자로 바뀌었다. 첫 번째 실행에서는 맞게 읽은 줄이다.
- 두 모델 모두 띄어쓰기와 칸 이름 아래의 묶음을 지켰다. 표는 한 줄에 칸을 나란히 적는 식으로 옮겼다.

데이터셋 25장의 결과다(11.9의 표에 더하는 줄).

| 읽은 것 | 글자 재현율 | 글자 정밀도 | 글자 F1 | 단어 F1 | 장당 시간 |
| :- | :- | :- | :- | :- | :- |
| `gpt-5.6-luna` | 64.6 | 94.5 | 76.8 | 60.8 | 6.1초 |

- 사진에서 `gpt-5.6-luna`는 Claude(93.5)와 macOS 내장 OCR(89.4)보다 낮고 PaddleOCR(69~74)보다 조금 높다. 읽은 것은 대체로 맞고(정밀도 94.5) 적지 않은 것이 많다(재현율 64.6).
- `gpt-4.1-mini`는 데이터셋으로 재지 않았다. 비용을 아끼려고 공고만 쟀다.

해석이다.

- 11.6에서 적은 걱정(LLM의 바꿔 쓰기)이 `gpt-5.6-luna`에서 실제로 나왔다. 글자 오류율은 가장 낮은 축이지만, 틀린 글자가 그럴듯해서 눈으로도 코드로도 찾기 어렵고 실행마다 달라진다. Claude가 읽은 결과(11.6)를 OpenAI의 싼 모델에 그대로 옮길 수 없다는 것도 확인되었다.
- `gpt-4.1-mini`는 온도 0에서 거의 같은 결과를 내고, 조건 줄을 두 번 모두 다 맞게 읽었고, 바꿔 쓴 것이 없었다. 띄어쓰기와 구조를 지키므로 PaddleOCR의 약점(11.3)이 없다. 설치할 것도 없다.
- 그래서 OpenAI의 모델로 읽는다면 추천 후보는 `gpt-4.1-mini`를 온도 0으로 쓰는 것이다. 걸리는 점은 세 가지다. 이 모델은 긴 변을 2,048픽셀로 줄이므로 잘라서 보내야 한다(3.2). 로고와 장식 글자를 빠뜨린다. 8조각을 두 번 읽은 것이 전부라, 다른 공고에서도 바꿔 쓰지 않는다고 보장할 수 없다.
- 남는 위험을 줄이는 방법은 세 가지다. 읽은 결과를 저장해 두고 다시 읽지 않는다(실행마다 달라지는 것을 막는다). 조건의 원문 구절이 읽은 글자 안에 있는지를 코드로 대조한다(`condition/condition.md`). 근거 화면에서 원본 이미지를 함께 보여 준다(`evaluation/evaluation.md`).
