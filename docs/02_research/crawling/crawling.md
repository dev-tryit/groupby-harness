# 수집 조사

사람인의 이미지 공고를, 공고 주소 하나에서 가져오는 방법을 조사한 문서. 근거는 `01_problem/problem.md`의 1.1 "만들 서비스"와 4.7 "수집은 핵심 문제가 아니다"다.

확인한 날짜는 2026-10-10이다. "직접 확인"이라고 적은 것은 그날 curl로 사람인에 요청해서 본 것이다. 사람인 공식 Open API는 호출하지 않았고, 로그인하지 않았다. 요청은 몇 초씩 쉬면서 보냈고, 합쳐서 66건이다(9장). 공고의 글자와 이미지는 저장소에 넣지 않았다.

## 1. 결론

공고 주소 하나에서 본문 이미지를 가져오는 절차는 네 단계다. 브라우저 없이 단순 HTTP 요청으로 된다(직접 확인).

1. 공고 주소에서 공고 번호(`rec_idx`)를 꺼낸다.
2. `https://www.saramin.co.kr/zf_user/jobs/relay/view-detail?rec_idx={번호}&rec_seq=0`을 GET으로 요청한다. 응답은 공고 본문만 담긴 작은 HTML이다(5~90KB).
3. 응답에서 `<div class="user_content">` 안의 `<img>` 태그의 `src`를 모은다. 장식 이미지(워터마크, 아이콘, 템플릿 머리 그림)는 호스트와 경로로 걸러낸다(4장).
4. 남은 `src`를 순서대로 GET으로 내려받는다.

함께 알아야 할 것은 네 가지다.

- 필요한 헤더는 `User-Agent` 하나다. curl의 기본 `User-Agent`로는 거절된다. `Referer`, 쿠키, 로그인은 필요 없었다(직접 확인).
- 거절될 때 HTTP 상태가 200으로 오는 경우가 있다. 상태 코드가 아니라 `Content-Type`이 이미지인지로 성공을 판단해야 한다(3장).
- 본문이 이미지뿐인 공고는 `user_content` 안에 글자가 0자에 가깝다. 다만 "이미지는 많은데 조건은 글자로 적힌" 공고가 있어서, 글자 수 하나로는 구별이 완전하지 않다(4장).
- 사람인의 기업회원 약관 제23조 제3항이 크롤링 등 자동화된 수단으로 접근하는 것과 정보를 수집하는 것을 금지한다(6장). 이 조사와 과제의 수집기도 이 조항에 해당하는 행위다. 어떻게 다룰지는 사용자가 정한다.

## 2. 페이지 구조

직접 확인한 구조다. 공고 하나를 보여주는 데 요청이 세 겹으로 일어난다.

| 겹 | 주소 | 방식 | 담긴 것 |
| :- | :- | :- | :- |
| 1. 겉 페이지 | `/zf_user/jobs/relay/view?rec_idx={번호}` | GET | 머리말, 메뉴, 스크립트. 공고 본문은 없다. 약 470KB. |
| 2. 요약 영역 | `/zf_user/jobs/relay/view-ajax` | POST (`rec_idx`, `rec_seq` 등) | 제목, 회사, 근무조건 요약, 그리고 본문을 가리키는 `iframe`. 약 125KB. |
| 3. 본문 | `/zf_user/jobs/relay/view-detail?rec_idx={번호}&rec_seq=0` | GET | 공고 본문. `iframe` 안에 실린다. 5~90KB. |

- 주소 형식: 검색 결과의 공고 링크는 `/zf_user/jobs/relay/view?view_type=search&rec_idx={번호}&...` 형태다. 겉 페이지의 `canonical` 주소는 `/zf_user/jobs/view?rec_idx={번호}`다. 어느 쪽이든 `rec_idx`만 있으면 된다.
- 겉 페이지는 스크립트(`jobs-view.js`)로 2번을 부르고, 2번의 응답에 `<iframe class="iframe_content" src="/zf_user/jobs/relay/view-detail?rec_idx=...&rec_seq=0&t_category=...">`가 들어 있다. 3번은 `rec_idx`와 `rec_seq=0`만 붙여 바로 요청해도 같은 본문이 온다. 그래서 수집기는 1번과 2번을 건너뛸 수 있다.
- 본문 HTML의 뼈대는 `<body>` 바로 아래에 `<div class="user_content">` 하나가 있고, 공고 내용 전체가 그 안에 있다. 그 뒤에는 스크립트만 있다.
- 본문 HTML의 `<head>`에는 `<meta name="robots" content="noindex,nofollow">`가 있다. robots.txt에는 `view-detail` 경로가 금지 목록에 없다(`law/law.md` 5장).

본문 이미지의 주소는 세 종류다.

| 호스트와 경로 | 무엇인가 | 태그의 특징 |
| :- | :- | :- |
| `pds.saramin.co.kr/recruit/recruit/{YYYYMM}/{DD}/{해시}_recruit.{확장자}` | 기업이 공고를 쓸 때 올린 이미지. 본문 이미지의 대부분이 이것이다. | `<img alt="업로드한 이미지" data-image-id="...">`. `alt`가 파일 이름인 경우도 있다. |
| `www.saraminimage.co.kr/recruit/{bbs_recruit숫자 또는 os_...}/...` | 사람인이 제작해 준 공고의 그림. 통짜 본문 그림도 있고, 아이콘·제목 띠·워터마크 같은 장식도 있다. | `alt`에 그림의 요약 글이 적힌 경우가 있다. |
| `static.saraminimage.co.kr/static/hiring/images/...` | 사람인 글자 템플릿의 머리 그림(`template/toptype/*.webp`)과 빈 그림(`blank.png`). 본문이 아니다. | |

- `src`는 `https://`로 시작하는 것과 `//`로 시작하는 것(프로토콜 생략)이 섞여 있다.
- 확장자는 `png`, `jpg`, `gif`, `webp`를 보았고, 대문자(`PNG`)도 있었다.
- 사람인 밖의 호스트를 가리키는 이미지도 있었다(이미지 호스팅 서비스, 다른 채용 사이트의 파일 서버). 8장에 적었다.

## 3. 단순 요청으로 되는지 확인한 결과

직접 확인했다. 쓴 `User-Agent`는 정체를 밝힌 문자열(`groupby-assignment-research/0.1 (...)`)이다. 브라우저를 흉내 낸 `User-Agent`는 쓰지 않았다.

| 요청 | 명령의 형태 | 응답 |
| :- | :- | :- |
| robots.txt, 헤더 없음 | `curl https://www.saramin.co.kr/robots.txt` | 307. 본문은 오류 페이지로 보내는 `meta refresh` 96바이트. |
| robots.txt, `User-Agent` 있음 | `curl -A "{UA}" https://www.saramin.co.kr/robots.txt` | 200. 정상. |
| 겉 페이지 | `curl -A "{UA}" ".../zf_user/jobs/relay/view?rec_idx={번호}"` | 200. 본문 없음. 세션 쿠키(`PHPSESSID`)를 내려준다. |
| 요약 영역 | `curl -A "{UA}" -e "{겉 페이지 주소}" -H "X-Requested-With: XMLHttpRequest" --data "rec_idx={번호}&rec_seq=0&view_type=..." ".../zf_user/jobs/relay/view-ajax"` | 200. `iframe` 주소가 들어 있다. |
| 본문 | `curl -A "{UA}" ".../zf_user/jobs/relay/view-detail?rec_idx={번호}&rec_seq=0"` | 200. 34건 모두 정상. `Referer`와 쿠키 없이 보냈다. |
| 이미지, `User-Agent` 있음 | `curl -A "{UA}" -o {파일} "https://pds.saramin.co.kr/recruit/recruit/..."` | 200, `image/png` 또는 `image/jpeg`. `Referer` 없이 보냈다. `www.saraminimage.co.kr`도 같다. |
| 이미지, 헤더 없음 | `curl "https://pds.saramin.co.kr/recruit/recruit/..."` | **200인데 `text/html` 422바이트.** 이미지가 아니다. |

읽은 것은 세 가지다.

- 막는 것은 curl의 기본 `User-Agent`다. `User-Agent`를 적으면 통과한다. 사람인이 `User-Agent`의 내용을 어디까지 보는지는 확인하지 않았다.
- 이미지 서버는 거절할 때도 200을 준다. 수집기는 응답의 `Content-Type`이 `image/`로 시작하는지, 또는 파일의 앞부분이 이미지 형식인지를 확인해야 한다.
- 요약 영역(2번)을 `Referer`와 `X-Requested-With` 없이 요청하면 되는지는 확인하지 않았다. 수집기가 2번을 쓰지 않으므로 확인하지 않았다.

차단은 겪지 않았다. 66건을 3~5초 간격으로 보내는 동안 응답이 달라지지 않았다. 더 많이, 더 빨리 보냈을 때 어떻게 되는지는 확인하지 않았다.

## 4. 이미지 공고를 구별하는 기준

본문 34건을 직접 확인해서 나눈 유형이다. 34건은 검색 결과에서 직군별로 골라 본 것이어서 비율에는 의미가 없다.

| 유형 | `user_content` 안의 글자 수 | `img` | 건수 | 이미지를 읽어야 조건이 나오는가 |
| :- | :- | :- | :- | :- |
| A. 이미지뿐 | 0자 (공백 문자만) | `pds.saramin.co.kr` 1~5장. 표(`table`) 없음. | 9 | 그렇다. 과제가 말하는 이미지 공고다. |
| B. 이미지와 짧은 글 | 40~190자 | 본문 그림 1~3장 + 글자 표 | 3 | 공고마다 다르다. 조건이 글자 표에 있고 그림은 회사 소개인 경우, 그림은 배너이고 표는 회사 채용 사이트로 가는 링크 목록인 경우를 보았다. |
| C. 글자 본문 + 부분 이미지 | 680~2,500자 | 글자 사이에 `pds` 이미지 1장 이상 | 5 | 아니다. 조건은 글자다. |
| D. 글자 본문 | 430~2,050자 | 장식(아이콘, 워터마크, 템플릿 머리 그림)만, 또는 없음 | 17 | 아니다. |

구별 기준의 후보는 이렇다. 정하는 것은 뒤 단계다.

1. 본문 이미지만 남긴다. `static.saraminimage.co.kr`의 그림, 주소에 `watermark`나 `icon`이 들어간 그림을 뺀다.
2. `user_content`에서 태그, 스크립트, `&nbsp;`를 지운 뒤 글자 수를 센다.
3. 글자 수가 0에 가깝고 본문 이미지가 1장 이상이면 유형 A다.

- 유형 A와 D는 글자 수가 0자와 430자 이상으로 크게 벌어져서 이 기준으로 갈린다.
- 유형 B는 글자 수만으로 A와 갈리지만, "조건이 이미지에 있는가"는 글자 수로 알 수 없다. 이미지를 읽어 봐야 안다.
- 사람인이 제작한 그림은 `alt`에 내용 요약이 글자로 들어 있는 경우가 있다(B에서 직접 확인). `alt`를 읽으면 이미지를 읽지 않고 글자를 얻게 되므로, 과제의 "이미지를 파싱한다"는 조건과 어긋날 수 있다.

## 5. 이미지의 형태

유형 A 가운데 8건, 유형 B 가운데 1건의 이미지 19장을 내려받아 직접 확인했다.

| 항목 | 확인한 값 |
| :- | :- |
| 장수 | 공고 하나에 1장이 5건, 3장이 3건, 5장이 1건 |
| 가로 | 860픽셀이 17장. 780픽셀 1장, 660픽셀 1장 |
| 세로 | 588~7,427픽셀. 1장짜리 공고는 750~4,300픽셀 |
| 용량 | 장당 34KB~2.6MB. 공고 하나의 합계는 149KB~7.0MB |
| 형식 | PNG 13장, JPEG 6장 |

- 가로는 본문 폭(860픽셀)에 맞춰져 있고, 세로로 긴 그림이다. 세로가 가로의 4~8배인 그림이 흔하다.
- 여러 장인 공고는 장마다 역할이 나뉜다. 회사 소개, 모집 조건, 복리후생이 각각 한 장인 식이다. 조건이 적힌 장은 그 가운데 하나였다(2건에서 직접 확인).
- 세로가 긴 그림을 통째로 줄여서 읽으면 글자가 작아진다. 860×7,427픽셀 그림을 긴 변 2,000픽셀로 줄이면 가로가 232픽셀이 되어 본문 글자를 읽기 어려웠다(직접 확인). 읽는 쪽에서 그림을 세로로 잘라야 할 수 있다. 이것은 읽기 조사의 주제다.
- 공고 하나의 픽셀 수는 약 50만(660×750)에서 약 1,750만(860×7,427 등 3장)까지 35배 차이가 났다. 이미지를 읽는 비용이 공고에 따라 그만큼 달라진다.

## 6. 사람인의 이용약관

2026-10-10에 사람인 사이트의 개인회원 약관과 기업회원 약관을 직접 확인했다. 두 약관 모두 "개정 및 적용 2026-01-22"라고 적혀 있다. 아래는 요약이고 원문이 아니다.

| 약관 | 조항 | 취지 |
| :- | :- | :- |
| 기업회원 약관 | 제23조 제3항 | 사람인이 데이터베이스제작자로서 권리를 가진다고 밝힌다. 사람인의 명시적인 사전 동의 없이 API 통신을 시도하는 것, 자동화된 수단(크롤링 등)으로 접근을 시도하는 것, 데이터베이스의 정보를 전부든 일부든 수집하는 것을 금지한다. |
| 기업회원 약관 | 제23조 제1항 | 기업회원이 올린 게시물의 저작권은 올린 기업회원이나 정당한 권리자에게 있다. 사람인은 서비스 제공과 개선을 위한 일부 이용 권한을 갖는다. |
| 기업회원 약관 | 제27조 제3항 | 기업회원이 아닌 이용자에게도 서비스 이용 범위 안에서 이 약관이 적용된다. |
| 개인회원 약관 | 제19조 제4항 | 서비스에서 얻은 정보를 사람인의 사전 동의 없이 복사·복제하거나 남에게 제공할 수 없다. |
| 개인회원 약관 | 제19조 제5항 | 서비스를 구직 이외의 목적으로 쓸 수 없다. 서비스의 안정적인 운영에 지장을 주는 행위, 사이트의 정보를 이용한 영리 행위를 금지한다. |

- 자동 수집을 직접 금지하는 조항은 있다. 기업회원 약관 제23조 제3항이다. "일부"의 수집도 금지 대상에 넣었다.
- 개인회원 약관에는 크롤링, 로봇, 자동화라는 낱말이 없다. 복제 금지와 구직 이외의 목적 금지가 있다.
- 해석: 고객사는 사람인의 기업회원이므로 기업회원 약관의 적용을 받는다. 그래서 "고객사 쪽에서 수집한다"는 구조(`law/law.md` 4장)에서도 고객사가 제23조 제3항을 어기게 될 수 있다. 한편 제23조 제1항에 따르면 공고의 저작권은 공고를 올린 고객사에게 있다. 고객사가 자기 공고의 원본 이미지를 직접 넣는 구조에서는 이 조항이 문제가 되지 않는다. 이 해석은 법률 자문이 아니다.
- 해석: 비회원이 로그인 없이 볼 때 약관이 적용되는지는 판례에서도 다투어진 점이다(`law/law.md` 3.2). 사람인은 제27조 제3항으로 비회원에게도 적용된다고 적어 두었다.
- 이 조사에서 보낸 요청과 과제의 수집기는 제23조 제3항이 금지하는 행위에 해당한다. 과제가 요구한 일이므로 적은 횟수로만 했고, 이 사실을 여기에 적어 둔다.

## 9. 확인하지 못한 것

- 마감된 공고와 없는 공고 번호를 요청했을 때의 응답.
- 요청을 더 많이, 더 빨리 보냈을 때 차단되는지와 그 기준. 시험하지 않았다.
- 사람인이 `User-Agent`의 내용을 어디까지 보는지. 브라우저의 `User-Agent`로는 요청하지 않았다.
- 브라우저에서 실제로 일어나는 요청의 전체 순서. 브라우저로 확인이 필요하다. 겉 페이지의 스크립트와 응답을 읽어서 추정했다.
- 모바일 사이트(`m.saramin.co.kr`)의 구조.
- 사람인 밖의 호스트에 있는 이미지(55074720)가 302로 어디로 보내는지. 따라가지 않았다.
- 후보 공고 가운데 열어 보지 않은 장의 내용(7장의 표에 적었다).
- 이미지 공고가 전체 공고에서 차지하는 비율. 확인한 34건은 골라서 본 것이다.
- 약관이 비회원의 자동 수집에 실제로 효력이 있는지. 법률 판단이고 `law/law.md`의 범위다.
- 사람인의 운영정책 등 약관 밖의 문서에 자동 수집에 관한 내용이 더 있는지.

이 조사에서 사람인에 보낸 요청은 66건이다. 내역은 robots.txt 2건, 검색 결과 5건, 겉 페이지 1건, 요약 영역 1건, 본문 34건, 이미지 21건(사람인 20건, 사람인 밖 1건. 같은 이미지를 헤더를 바꿔 두 번 요청한 1건 포함), 약관 2건이다.
