# 조건 조사

공고에 나오는 조건의 종류와 구조, 그리고 직군에 기대지 않고 조건을 뽑는 방법을 조사한 문서. 근거는 `01_problem/problem.md`의 1.2 "3. 조건 추출", 4.1, 4.2, 4.7, 5장이다.

이 문서는 공개된 표준 문서, 논문, API 문서를 읽고 정리한 것이다. 실제 사람인 공고를 열어 보지 않았고, 추출을 직접 돌려 보지도 않았다. 사람인은 Open API의 안내 문서만 읽었고 API를 호출하지 않았다. 조건 스키마를 정하는 문서가 아니다. 선택지와 추천 후보까지만 적는다. 확인한 날짜는 2026-10-10이다.

"확인"이라고 적은 것은 출처에서 읽은 사실이고, "해석"이라고 적은 것은 조사자의 추측이다.

## 1. 결론

- 공고의 항목 이름(자격요건, 우대사항 등)은 직군마다 달라지지만, 조건이 가질 수 있는 **형식**은 몇 가지로 닫힌다(해석). 형식은 "얼마 이상인가(수치)", "어느 단계 이상인가(순서 범주)", "갖고 있는가(보유)", "해 봤는가·할 수 있는가(서술)", "받아들일 수 있는가(제약)"다.
- 추천 후보는 **형식은 닫힌 집합으로, 대상(무엇에 관한 조건인지)은 열린 글자로** 두는 틀이다(3장의 B). 직군에 관한 지식은 대상 쪽에만 들어가고, 코드는 형식만 안다.
- 기존 표준(schema.org, O\*NET, ESCO, NCS)은 조건을 "학력, 경력, 자격, 스킬" 같은 **항목**으로 나눈다. 필수와 우대를 공고 단위로 구분하는 필드는 schema.org JobPosting에 없다(확인). 표준을 그대로 스키마로 쓰기보다 항목 이름의 참고로 쓰는 것이 맞다(해석).
- 스킬 사전이나 직군별로 학습한 모델에 기대는 방식은 새 직군에서 약하다. LLM은 사전 없이 뽑지만, 원문을 고쳐 쓰고, "A 및 B"를 하나로 묶고, 조건이 아닌 것을 조건으로 뽑는다(확인, 6장).
- 그래서 조건마다 **원문 구절**을 갖게 하고, 그 구절이 읽은 글자 안에 실제로 있는지를 코드로 확인하는 것이 핵심 대책이다. 이 원문 구절은 뒤 단계에서 근거의 출처로 그대로 쓰인다.

## 2. 공고에 나오는 조건의 종류

항목 목록은 과제 설명, 사람인 Open API 안내 문서의 응답 항목, schema.org JobPosting의 속성을 합쳐 만든 것이다. "지원자와 맞대는가"와 "형식"은 해석이다.

### 2.1 지원자와 맞대는 조건

| 항목 | 조건이 나오는 모양(일반화) | 형식 | 이력서에서 맞대는 것 |
| :- | :- | :- | :- |
| 경력 | 신입, 경력 N년 이상, N~M년, 경력 무관 | 수치 범위 | 경력 기간의 합 |
| 유관 경력 | 특정 업무·업종·직무의 경력 N년 이상 | 수치 범위 + 서술 | 그 업무에 해당하는 경력의 기간 |
| 학력 | 학력 무관, 고졸 이상, 초대졸 이상, 대졸 이상, 석사 이상 | 순서 범주 | 최종 학력 |
| 전공 | 특정 계열 전공자, 관련 학과 | 범주(열린 값) | 전공 |

| 도구·기술 | 특정 프로그램·장비·언어를 다룰 수 있는 사람 | 보유 여부 또는 서술 | 보유 기술, 경력 내용 |

| 성격·태도 | 책임감, 소통 능력, 꼼꼼함 | 서술 (확인하기 어려움) | 자기소개. 대부분 근거가 없다 |
| 근무지 | 지역, 재택 여부 | 제약 | 거주지, 희망 근무지 |
| 고용형태 | 정규직, 계약직, 인턴, 파견 | 제약 | 희망 고용형태 |
| 근무시간·교대 | 주간, 교대, 주말 근무 | 제약 | 희망 조건(대개 이력서에 없음) |
| 급여 | 연봉 범위, 회사 내규, 면접 후 결정 | 제약 | 희망 연봉(대개 이력서에 없음) |
| 병역 | 군필 또는 면제 | 보유 여부 | 병역 사항 |
| 우대 대상 | 보훈 대상자, 장애인, 인근 거주자, 즉시 출근 가능자 | 보유 여부 | 해당 여부 |

### 2.2 지원자와 맞대지 않는 정보

| 항목 | 맞대지 않는 이유 |
| :- | :- |
| 회사 소개, 사업 내용 | 지원자의 속성이 아니다. |
| 복리후생 | 회사가 주는 것이다. |
| 전형절차, 접수 기간·방법, 제출서류 | 절차다. 지원자의 자격이 아니다. |
| 모집 인원 | 지원자의 속성이 아니다. |
| 모집부문 이름, 직급 | 조건이 아니라 조건들을 묶는 이름이다. 한 공고에 모집부문이 여럿이면 조건을 모집부문별로 나누는 기준이 된다. |

담당업무는 경계에 있다. 공고가 "이 업무를 해 본 사람"이라고 쓰지 않았어도, 사람은 담당업무와 경력이 겹치는지를 본다. 담당업무를 조건으로 볼지, 조건을 해석하는 배경으로만 볼지는 정해야 한다(해석).

### 2.3 법으로 요구할 수 없는 조건

공고에 나올 수 있지만 점수에 쓰면 안 될 수 있는 조건이다. 아래는 기사와 법률 해설에서 읽은 것이고, 조문 원문은 읽지 못했다.

| 조건 | 관련된 법 | 내용 |
| :- | :- | :- |
| 성별 | 남녀고용평등법 제7조 | 모집·채용에서 남녀를 차별할 수 없다. 직무에 필요하지 않은 용모·키·체중, 미혼 조건을 요구할 수 없다. |
| 연령 | 고령자고용법 제4조의4 | 합리적인 이유 없이 연령을 이유로 차별할 수 없다. |
| 용모·키·체중, 출신지역, 혼인 여부, 재산, 가족의 학력·직업·재산 | 채용절차법 제4조의3 | 직무 수행에 필요하지 않으면 요구할 수 없다. 상시 근로자 30명 이상 사업장에 적용된다. |

이런 조건을 추출은 하되 점수에서 빼고 표시만 할지, 추출도 하지 않을지는 사용자가 정할 일이다.

### 2.4 직군별 공통점과 차이

실제 공고를 직군별로 모아 확인하지 않았다. 아래는 해석이다.

- 공통: 경력, 학력, 고용형태, 근무지는 거의 모든 직군의 공고에 나온다. 사람인 Open API도 이 네 가지를 직군과 무관한 고정 항목으로 준다(확인, 4장).
- 차이는 **어떤 형식의 조건이 많은가**에서 난다. 면허나 자격이 있어야 일할 수 있는 직군은 보유 여부 조건이 필수로 나온다. 사무·영업·기획 쪽은 서술 조건의 비중이 크다. 생산·현장 쪽은 교대 근무, 근무지, 체력 같은 제약 조건이 앞에 나온다.
- 직군이 달라져도 새 형식이 생기지는 않는다고 본다. 달라지는 것은 대상의 이름(무슨 자격증, 무슨 도구)과 형식별 비중이다. 이것이 형식을 일반화의 축으로 삼는 근거다.

## 3. 직군과 무관하게 조건을 나누는 틀

### 3.1 선택지

| | A. 항목 기반 고정 필드 | B. 형식 기반 조건 목록 | C. 원문 구절만 |
| :- | :- | :- | :- |
| 모양 | 공고 하나가 `경력`, `학력`, `자격증[]`, `스킬[]` 같은 정해진 칸을 갖는다. | 공고 하나가 조건의 목록을 갖는다. 조건마다 형식(닫힌 집합), 대상(열린 글자), 값, 필수/우대, 원문 구절을 갖는다. | 공고 하나가 조건의 목록을 갖는다. 조건은 원문 구절과 필수/우대만 갖는다. |
| 비교 방식 | 칸마다 정해진 비교 코드 | 형식마다 정해진 비교 코드. 서술 형식만 LLM | 전부 LLM |
| 장점 | 가장 단순하다. 기존 표준과 같은 모양이다. 경력·학력은 결정론으로 비교된다. | 형식이 몇 개뿐이라 직군이 늘어도 코드가 늘지 않는다. 수치·순서·보유 형식은 결정론으로 비교된다. 조건 하나가 근거 하나에 대응한다. | 스키마가 틀릴 일이 거의 없다. 추출이 가장 쉽다. |
| 단점 | 칸에 없는 조건은 `기타`로 떨어지거나 사라진다. 칸을 늘리면 그것이 곧 직군 하드코딩이다. | 추출이 가장 어렵다. LLM이 형식을 잘못 고르거나 문장을 잘못 나눌 수 있다. 형식 분류가 틀리면 비교도 틀린다. | 비교가 모두 LLM이라 비용이 지원자 수 × 조건 수로 늘고, 점수가 LLM의 말에 기댄다. "경력 3년 이상"처럼 계산할 수 있는 것도 계산하지 않는다. |
| 직군 일반화 | 약하다. | 강하다. | 강하다. |
| 예산과의 관계 | LLM 호출이 가장 적다. | 공고당 추출 1회와 서술 조건의 비교에만 쓴다. | 가장 많이 쓴다. |

### 3.2 추천 후보

B를 추천 후보로 둔다. 이유는 세 가지다(해석).

- `problem.md` 4.2의 "직군이 아니라 조건의 형식을 일반화한다"와 모양이 같다.
- `problem.md` 4.3의 "LLM이 내놓은 숫자는 실제 수치가 아니다"와 4.6의 비용 제약을 함께 만족한다. 계산할 수 있는 조건은 코드가 계산하고, LLM은 서술 조건에만 쓴다.
- A의 고정 칸은 B에서 "대상"의 값으로 흡수된다. 예를 들어 A의 `학력` 칸은 B에서 "형식: 순서 범주, 대상: 학력"인 조건 하나다.

B가 실제 공고에서 무너지면 C로 물러설 수 있다. B의 조건은 C의 조건(원문 구절, 필수/우대)을 포함하기 때문이다.

### 3.3 B에서 형식의 후보

| 형식 | 묻는 것 | 예 | 비교 |
| :- | :- | :- | :- |
| 수치 범위 | 얼마 이상·이하인가 | 경력 3년 이상, 어학 점수 800점 이상 | 숫자 비교 |
| 순서 범주 | 어느 단계 이상인가 | 초대졸 이상 | 단계의 순서 비교 |
| 보유 여부 | 갖고 있는가 | 특정 자격증, 운전면허, 병역 | 이름의 일치(표기가 다르면 LLM 또는 유사도) |
| 서술 | 해 봤는가, 할 수 있는가, 그런 사람인가 | 특정 업무 경험, 소통 능력 | LLM이 이력서 구절을 찾아 판정 |
| 제약 | 지원자가 받아들일 수 있는가 | 근무지, 고용형태, 교대 근무 | 이력서에 정보가 있으면 일치 비교, 없으면 판정 불가 |

정할 것이 남는다. 순서 범주의 단계 목록(학력의 순서)은 직군과 무관하지만 코드에 들어가야 한다. 전공처럼 순서가 없는 범주를 보유 여부로 볼지 따로 둘지도 정해야 한다. 성격·태도를 서술 형식 안에 둘지, "이력서로 확인하기 어려움"으로 따로 표시할지도 정해야 한다.

### 3.4 조건 하나가 가질 수 있는 필드의 후보

| 필드 | 내용 | 필요한 이유 |
| :- | :- | :- |
| 원문 구절 | 읽은 글자에서 그대로 가져온 구절 | 추출을 검증하고, 근거의 출처로 쓴다. |
| 출처 위치 | 몇 번째 이미지, 어느 항목 제목 아래, 글자 위치 | 사람이 공고에서 그 자리를 찾는다. |
| 필수/우대 | 필수, 우대, 알 수 없음 | 점수에서 무게가 다르다. "알 수 없음"이 없으면 LLM이 억지로 고른다. |
| 형식 | 3.3의 닫힌 집합 | 비교 방식을 정한다. |
| 대상 | 무엇에 관한 조건인지(열린 글자) | 직군에 관한 내용이 들어가는 유일한 곳이다. |
| 연산자, 값, 단위 | 이상·이하·범위·같음, 숫자나 단계, 년·점 | 수치 범위와 순서 범주를 계산한다. |
| 한정어 | "유관", "관련", "~에 준하는" 같은 범위를 흐리는 말 | 조건이 모호하다는 것을 판정과 근거에 드러낸다. |
| 대안 묶음 | "A 또는 B"로 묶인 조건들의 묶음 번호 | 하나만 충족해도 되는 조건을 따로 감점하지 않는다. |
| 모집부문 | 조건이 속한 모집부문 | 한 공고에 모집부문이 여럿일 때 조건이 섞이지 않게 한다. |
| 확인 가능 여부 | 이력서로 확인할 수 있는 조건인지 | "충족하지 않음"과 "알 수 없음"을 나눈다. |

## 4. 기존 표준이 조건을 나누는 방식

| 표준 | 조건을 나누는 방식 (확인) | 이 과제에 주는 것 (해석) |
| :- | :- | :- |
| schema.org JobPosting | 속성이 36개다. 조건에 해당하는 것은 `educationRequirements`, `experienceRequirements`, `qualifications`, `skills`, `physicalRequirement`, `sensoryRequirement`, `securityClearanceRequirement`, `eligibilityToWorkRequirement`다. 근무 조건은 `employmentType`, `jobLocation`, `jobLocationType`, `workHours`, `baseSalary`, `jobDuration`이다. `responsibilities`, `jobBenefits`, `employerOverview`는 따로 있다. `experienceInPlaceOfEducation`은 경력이 학력을 대신할 수 있는지를 나타낸다. 대부분의 값은 글자(Text)를 허용한다. | 항목 이름의 참고가 된다. 필수와 우대를 나누는 속성은 없다. `skills`의 설명은 "요구되거나 바라는" 것을 한데 묶는다. `experienceInPlaceOfEducation`은 대안 묶음(A 또는 B)이 표준에도 필요했다는 예다. |

표준들에서 읽은 것(해석):

- 표준은 모두 항목으로 나눈다. 형식으로 나눈 표준은 찾지 못했다.
- 표준은 값을 글자로 두는 경우가 많다. 구조화가 어렵다는 것을 표준도 받아들였다는 뜻이다.
- 필수와 우대의 구분, 대안(또는), 원문 구절의 위치는 표준에서 빌려 올 것이 거의 없다. 이 과제에서 직접 설계해야 한다.

### 5.3 추천 후보

혼합을 추천 후보로 둔다(해석).

1. 읽은 글자를 항목 제목으로 나눈다(규칙). 제목을 찾지 못하면 통째로 넘긴다.
2. LLM이 조건의 목록을 구조화 출력으로 낸다. 조건마다 원문 구절을 함께 낸다. 공고 하나에 한 번 호출한다.
3. 코드가 원문 구절이 읽은 글자 안에 있는지 확인한다. 없는 조건은 버리거나 표시한다.
4. 수치(연수, 점수)는 원문 구절에서 정규식으로 다시 뽑아 LLM이 낸 값과 맞는지 확인한다.

LLM 호출은 공고 하나에 한 번이고 지원자 수와 무관하다. 그래서 비용은 비교 단계보다 작을 것으로 본다. 실제 비용은 계산하지 않았다.

## 6. 알려진 실패와 대책

### 6.1 Nguyen 외의 실패 분석 (확인)

LLM이 틀린 예 60개를 사람이 분류한 결과다. 한 예가 여러 갈래에 속할 수 있다.

| 갈래 | 비율 | 내용 |
| :- | :- | :- |
| 정의가 어긋남 | 약 36% | 스킬은 아니지만 직업과 관련된 말을 스킬로 뽑았다. |
| 틀린 추출 | 20% | 스킬과 무관한 구절을 뽑았다. |
| 묶인 조건 | 약 14% | "A 및 B를 개발하는 능력"처럼 두 조건이 한 구절에 든 것을 나누지 못했다. 여섯 데이터셋 중 넷에서 구간의 16~22%가 이런 묶인 조건이었다. |
| 구간이 길어짐 | 약 12% | 정답보다 긴 구절을 뽑았다. |
| 그 밖 | 약 10% | 출력 형식을 지키지 않았다. |

같은 논문이 적은 다른 사실은 이렇다.

- LLM은 원문을 그대로 옮기지 못한다. 원문의 오타와 띄어쓰기를 스스로 고쳐서, 뽑은 구절이 원문과 일치하지 않게 된다.
- 논문은 공백과 문장부호의 차이를 규칙으로 보정했고, 그래도 맞지 않으면 틀린 점을 알려 주고 다시 요청하기를 3번까지 했다.
- 예시 없이 요청하면 형식 실패가 가장 많았다(추출 방식에서 평균 약 27%). 예시를 주면 약 2~4%로 줄었다.

이 과제에서 "원문"은 OCR이 읽은 글자다. OCR 글자에는 오타와 깨진 띄어쓰기가 있으므로 LLM이 고쳐 쓸 가능성이 더 크다(해석).

### 6.2 실패와 대책

대책은 해석이다. 직접 돌려 확인하지 않았다.

| 실패 | 대책의 후보 |
| :- | :- |
| 원문에 없는 조건을 지어낸다. | 조건마다 원문 구절을 내게 하고, 코드가 읽은 글자 안에 그 구절이 있는지 확인한다. 없으면 버리거나 "검증 실패"로 표시한다. |
| 원문 구절을 고쳐 써서 일치하지 않는다. | 공백과 문장부호를 지운 뒤 비교한다. 그래도 맞지 않으면 유사도로 가장 가까운 자리를 찾고 점수를 남긴다. LangExtract는 찾지 못한 추출의 위치를 비워 두어 걸러 낼 수 있게 한다(확인). |
| 필수와 우대를 섞는다. | 규칙으로 나눈 항목 제목을 LLM에 함께 주고, 필수/우대를 제목에서 정한다. 제목이 없으면 "알 수 없음"을 허용한다. 문장 안의 "우대", "필수", "가능자" 같은 표지어를 코드로 다시 확인한다. |
| 묶인 조건을 나누지 못한다. | "및", "또는", 쉼표, 가운뎃점으로 이어진 문장을 나누는 예시를 준다. 나눈 조건들이 같은 원문 구절을 가리키게 하고, "또는"이면 대안 묶음 번호를 준다. |
| "및"과 "또는"을 뒤바꾼다. | 묶음의 종류(모두, 하나 이상)를 필드로 받는다. 원문 구절에 "또는", "혹은", "중 하나"가 있는지 코드로 확인한다. |
| 모호한 표현("유관 경력", "관련 학과", "~에 준하는")을 임의로 풀어 쓴다. | 풀어 쓰지 않고 원문 표현 그대로 대상에 둔다. 한정어 필드에 모호하다는 것을 남긴다. 무엇이 "유관"인지는 비교 단계가 담당업무를 보고 판정하고, 근거에 모호했다는 것을 적는다. |
| 조건이 아닌 것(복지, 전형절차, 회사 소개)을 조건으로 뽑는다. | 항목 제목으로 먼저 걸러 낸다. 스키마에 "조건이 아님"을 고를 수 있게 한다. |
| 수치를 잘못 옮긴다("3년 이상"을 5로, "이상"을 "이하"로). | 원문 구절에서 정규식으로 숫자와 연산자를 다시 뽑아 LLM의 값과 비교한다. |
| 같은 공고에서 실행할 때마다 조건이 달라진다. | 온도를 0으로 둔다. 추출 결과를 저장해 다시 쓴다. 조건은 사람이 고칠 수 있게 한다(`problem.md` 1.1의 4번). |
| OCR이 틀리게 읽은 글자를 그대로 조건으로 만든다. | 추출 단계에서는 막을 수 없다. 원문 구절과 출처 위치를 사람에게 보여 주어 이미지와 대조하게 한다. |
| 스키마에 맞는 JSON이지만 내용이 틀리다. | 구조화 출력은 형식만 보장하고 값이 옳은지는 보장하지 않는다(확인). 위의 검증을 따로 둔다. |

### 6.3 인용 기능과 구조화 출력 (확인)

Anthropic의 문서에서 확인한 것이다. 다른 회사의 API는 확인하지 않았다.

- 구조화 출력은 응답이 JSON 스키마를 따르게 한다. 숫자의 최소·최대, 문자열 길이, 재귀 스키마는 지원하지 않는다. 거절하거나 토큰 한도에 걸리면 스키마에 맞지 않을 수 있다.
- 인용(Citations) 기능은 문서에서 가져온 구절과 그 글자 위치를 준다. 인용이 문서의 실제 위치를 가리킨다는 것을 API가 보장하고, 인용된 구절은 출력 토큰으로 세지 않는다.
- **인용 기능과 구조화 출력은 함께 쓸 수 없다.** 함께 요청하면 오류가 난다.

그래서 길이 둘로 갈린다(해석). 구조화 출력을 쓰고 원문 구절은 필드로 받아 코드로 검증하거나, 인용 기능을 쓰고 응답 글자를 직접 구조로 바꾸는 것이다. 앞쪽이 스키마를 다루기 쉽고, 검증을 코드가 맡으므로 특정 API에 묶이지 않는다.

## 7. 뒤 단계에 주는 영향

### 7.1 비교(판정)

조건의 형식이 비교 방식을 정한다(해석).

| 형식 | 비교 방식 | LLM | 판정이 가질 수 있는 값 |
| :- | :- | :- | :- |
| 수치 범위 | 이력서에서 구한 숫자와 비교 | 쓰지 않는다. 다만 이력서에서 경력 기간을 구하는 일은 따로 풀어야 한다. | 충족, 미충족, 얼마나 모자라는지 |
| 순서 범주 | 단계의 순서 비교 | 쓰지 않는다. | 충족, 미충족 |
| 보유 여부 | 이름의 일치 | 표기가 다를 때만 쓴다. | 있음, 없음, 비슷한 것이 있음 |
| 서술 | 이력서에서 해당하는 구절을 찾아 판정 | 쓴다. | 충족, 일부 충족, 근거 없음 |
| 제약 | 이력서에 정보가 있으면 일치 비교 | 쓰지 않는다. | 충족, 미충족, 알 수 없음 |

- 수치 범위는 "얼마나 모자라는지"가 나온다. `problem.md` 3장의 "부분 매칭이 무엇이 부분인지"를 정할 때 쓸 수 있다. 경력 3년 이상에 2년 10개월인 지원자와 6개월인 지원자는 둘 다 미충족이지만 같지 않다.
- 서술과 제약은 "알 수 없음"이 자주 나온다. 이력서에 적혀 있지 않은 것과 충족하지 않는 것을 나눠야 점수와 근거가 정직해진다.
- 유관 경력처럼 수치와 서술이 겹친 조건은 두 단계가 필요하다. 어느 경력이 "유관"인지를 LLM이 고르고, 그 경력의 기간을 코드가 더한다.
- 대안 묶음은 묶음 단위로 판정해야 한다. 조건별로 판정하면 "A 또는 B"에서 A만 가진 지원자가 감점된다.
- 필수/우대는 점수의 무게를 가른다. 필수 미충족을 감점으로 볼지 탈락으로 볼지는 점수 단계에서 정할 일이다.

### 7.2 근거

- `problem.md` 1.2의 6번은 근거가 "공고의 어느 조건"을 가리키라고 한다. 조건이 원문 구절과 출처 위치를 갖고 있지 않으면 근거가 가리킬 곳이 없다. 원문 구절은 추출의 검증과 근거의 출처에 함께 쓰인다.
- 조건 하나가 근거 한 줄에 대응하면 사람이 조건별로 동의하거나 고칠 수 있다. `problem.md` 1.1의 4번, 5번(사람의 판단이 데이터로 남는다)이 조건 단위로 쌓인다.
- 한정어와 "알 수 없음"을 근거에 드러내면, 사람은 시스템이 모호하다고 본 곳을 먼저 확인할 수 있다.
- 읽기를 고객사 쪽에 두면 서버는 이미지를 갖지 않는다(`law/law.md` 4장). 그러면 출처 위치는 이미지 좌표가 아니라 읽은 글자 안의 위치가 된다.

## 8. 깨질 수 있는 지점 (테스트 케이스 후보)

| 지점 | 무엇이 깨지는가 |
| :- | :- |
| 항목 제목이 없는 공고 | 필수와 우대를 나눌 근거가 없다. |
| 표로 된 공고(모집부문별 행) | OCR이 행과 열을 섞으면 조건이 다른 모집부문에 붙는다. |
| 한 공고에 모집부문이 여럿 | 조건이 섞인다. 어느 모집부문에 지원한 지원자인지도 정해야 한다. |
| "A 또는 B" | 조건 둘로 나뉘어 하나만 가진 지원자가 감점된다. |
| "A 및 B 경험" | 조건 하나로 묶여 하나만 가진 지원자가 충족으로 판정된다. |
| "유관 경력 N년 이상" | 총 경력으로 계산해 충족으로 판정한다. |
| "관련 학과", "~에 준하는 자격" | 범위를 LLM이 임의로 정한다. |
| "신입/경력", "경력 무관", "N년 이상(신입 지원 가능)" | 수치 범위로 옮길 때 하한이 0인지 N인지가 갈린다. |
| "초대졸 이상", "고졸 이상(졸업 예정자 가능)" | 단계의 순서와 예정자 처리가 갈린다. |
| 자격증의 표기 차이(약칭, 급수, 옛 이름) | 이름이 일치하지 않아 "없음"으로 판정한다. |
| 우대사항 안에 필수처럼 쓴 문장, 자격요건 안의 "우대" | 제목과 문장의 표지어가 어긋난다. |
| 성격·태도만 있는 공고 | 확인할 수 있는 조건이 거의 없어 점수가 근거 없이 나온다. |
| 조건이 한두 개뿐인 공고 | 조건 하나의 판정이 점수 전체를 좌우한다. |
| 복리후생이나 전형절차의 문장이 조건으로 뽑힘 | "자격증 취득 지원" 같은 복지가 자격증 조건이 된다. |
| OCR 오타 | 원문 구절 검증이 실패하거나, 숫자가 다르게 읽혀 조건이 바뀐다. |
| 성별·연령 같은 요구할 수 없는 조건 | 점수에 들어가면 차별이 된다. |
| 서로 다른 직군의 공고 2개 | 한쪽에서만 통하는 형식이나 프롬프트 예시가 드러난다. |

마지막 줄이 과제의 "서로 다른 직군 2개"가 확인하려는 것이다(해석). 프롬프트의 예시가 한 직군에 치우치면 다른 직군의 조건을 그 예시에 맞춰 뽑을 수 있다. 예시의 직군을 평가에 쓰는 공고의 직군과 다르게 두는 것이 한 가지 방법이다.

## 9. 확인하지 못한 것

- 실제 사람인 이미지 공고의 모양. 공고를 열어 보지 않았다. 2장의 종류와 2.4의 직군별 차이는 일반론과 해석이다.
- 사람인의 공고 등록 화면이 기업에게 받는 항목
- 사람인 Open API의 고용형태, 학력, 급여 코드표 전체 (안내 문서의 예시 값만 보았다)
- 고용24(워크넷) 구인신청서의 전체 항목과 직업안정법 시행규칙의 서식
- HR Open Standards의 PositionOpening 스키마가 조건을 나누는 필드
- KECO의 현행 분류 개수, NCS 직업기초능력 10개 영역의 전체 이름과 현행 분류 개수
- ESCO의 한국어 지원 여부
- 2.3의 법 조문 원문 (기사와 해설만 보았다)
- 한국어 공고에서 필수/우대 구분이나 조건 전체를 추출한 연구 (IT 직종을 다룬 학위논문 하나만 찾았고, 초록만 읽었다)
- LLM이 한국어 공고에서 조건을 얼마나 정확히 뽑는지. 6.1의 수치는 영어·프랑스어·독일어·덴마크어와 GPT-3.5 기준이라 지금의 모델과 한국어에 그대로 맞는다고 볼 수 없다.
- 6.2의 대책이 실제로 통하는지. 직접 돌려 보지 않았다.
- 추출에 드는 실제 비용
- LangExtract의 일치 방식의 세부 (저장소의 설명만 보았고 코드는 읽지 않았다)
- Anthropic 외 다른 API의 구조화 출력과 인용 기능
