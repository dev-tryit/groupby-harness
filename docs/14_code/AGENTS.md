# 14_code

실제 코드 구현을 담는 폴더. 설계 내용은 앞 단계 폴더(`00`~`13`)에 둔다.

코드 아키텍처는 별도 설계 단계를 두지 않고 이 파일에 규칙으로 둔다.

## 아키텍처

- 코드는 헥사고날 아키텍처로 쓴다. 이유는 테스트가 쉽기 때문이다.

## 프론트엔드, 백엔드, 인프라의 분리

- 프론트엔드, 백엔드, 인프라는 처음부터 폴더 단위로 나눈다. `frontend/`, `backend/`, `infra/`에 각각 둔다.
- 인프라 코드는 `infra/`에 둔다. 무엇을 만들지는 `09_infra`의 설계를 따른다.
  - `infra/local/` — 로컬 구성. Docker Compose로 쓴다.
  - `infra/server/` — 서버(클라우드) 구성. Pulumi로 쓴다.
  - 이번 과제는 로컬 구성만 만든다. `infra/server/`는 비워 두고 그 이유를 적은 `README.md` 하나만 둔다. 평가자가 자기 컴퓨터에서 명령 하나로 실행해야 하기 때문이다. 클라우드에 의존하면 평가자에게 계정과 키가 필요해진다.
- 코드가 실행되며 만든 데이터(예: 크롤링한 이미지, DB 파일)는 git에 올리지 않는다.
- Next.js처럼 프론트엔드와 백엔드가 합쳐진 프레임워크를 쓰더라도, 가능하면 폴더 단위로 나눈다.
- 이유는 두 쪽의 코드가 서로 얽혀 스파게티 코드가 되는 것을 막기 위해서다. 스파게티 코드를 막아야 나중에 리팩토링할 때 서로에게 미치는 영향을 파악할 수 있다.

## 서브모듈

`frontend/`, `backend/`, `infra/`는 각각 별도 레포이고, 이 레포에 git 서브모듈로 연결되어 있다.

| 폴더 | 레포 |
| :- | :- |
| `frontend/` | `dev-tryit/groupby-frontend` |
| `backend/` | `dev-tryit/groupby-backend` |
| `infra/` | `dev-tryit/groupby-infra` |

- 나누는 이유는 두 가지다. 코드 레포를 각각 관리하기 위해서이고, GitHub Actions를 레포(환경)마다 다르게 설정할 일이 많기 때문이다.
- 서브모듈도 이 레포와 같은 이름의 버전 브랜치에서 개발한다. 지금은 `v1.0.0`이다.
- 코드를 고치면 커밋을 두 번 한다. 먼저 서브모듈 레포에 커밋하고 푸시한 뒤, 이 레포에서 서브모듈이 가리키는 커밋을 갱신해 커밋한다. 순서를 바꾸면 이 레포가 원격에 없는 커밋을 가리키게 된다.
- 서브모듈의 커밋도 `commit-reports/AGENTS.md`의 커밋 절차를 따른다. 보고서는 이 레포의 `commit-reports/`에 하나만 쓴다.
- 이 레포를 받을 때는 `git clone --recursive`로 받는다. 그냥 받으면 코드 폴더가 비어 있다.
