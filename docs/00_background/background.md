# 백그라운드

이 프로젝트가 무엇을 위한 것이고, 무엇을 만들어야 하며, 누가 무엇으로 평가하는지를 정리한 문서.

## 1. 지원 상황

- 이 프로젝트는 그룹바이에이치알의 채용 과제를 수행하는 저장소다.
- 지원자는 김동현이다. 그룹바이에이치알의 AI 엔지니어 채용 공고에 지원했다. 공고 내용은 5장에 있다.
- 1차 서류에 합격했고, 공동 대표인 박상민 CSO와 미팅을 했다. 채용 공고를 쓴 사람도 박상민 CSO다.
- 그 미팅에서 과제 설명을 들었고, 이후 메일로 과제 안내 HTML을 받았다. 메일 내용은 3장에, 과제 내용은 4장에 있다.
- 지금은 과제를 수행하는 단계다.

### 기한

- 과제 소요 최대 시간은 24시간이다. 이 24시간을 기준으로 삼는다.
- **듀데이트는 2026-10-11(일) 20:00이다.**
- 시작 시각은 과제 파일을 내려받은 2026-10-10 20:22다. 정확히 24시간 뒤는 2026-10-11 20:22다. 남는 22분은 제출 전 마지막 확인과 메일 발송에 쓴다.
- 24시간은 누가 재는 것이 아니다. 양심상 24시간 내외로 맞춘다.
- 메일이 말한 제출 기한은 월요일(2026-10-12) 자정 전이다. 듀데이트가 그보다 앞서므로, "자정"이 0시인지 24시인지는 따지지 않는다.

## 2. 이 과제에서 초점을 두는 것

지원자가 정한 방향이다.

- 쓸 수 있는 시간은 24시간 내외다. 전부 만들 수 없으므로, 무엇을 먼저 하고 무엇을 뒤로 미뤘는지 우선순위의 순서를 정직하게 보여주는 것이 중요하다.
- 초점은 두 가지다.
  - 앞으로 개발할 때 계속 활용할 하네스를 만드는 것
  - 문제를 잘 해결하는 것

## 3. 과제 안내 메일

과제 안내 HTML과 함께 받은 메일이다. 보낸 사람은 박상민 CSO다. 연락처(전화번호, 메일 주소)는 이 문서에 적지 않는다. 레포가 public이기 때문이다.

>
> 과제 소요 최대 시간은 24시간이며, 월요일 자정 전까지 공유해주시면 될 것 같습니다.
> 과제 진행을 위해 궁금한 점이 있으시다면 언제든지 편히 회신 부탁드립니다.

- 궁금한 점은 메일 회신으로 물어볼 수 있다.

## 4. 과제 안내: 지원자-공고 매칭 스코어링 엔진

그룹바이가 전달한 과제 안내 HTML의 내용이다.

### 기본 조건

| 항목 | 내용 |
| :- | :- |
| 예상 소요시간 | 24시간 내외 |
| 사용 언어/스택 | 자유 (특정 프레임워크 요구 없음) |
| 제출물 | GitHub public 레포 링크 (코드 + README) |
| 마감 | 과제를 전달받은 시점으로부터 24시간 이내. 준비되는 대로 전달한다. |

- 24시간 안에 전부 완성하지 못해도 된다. 중요하다고 판단하는 부분 위주로 우선순위를 정해서 진행하고, 과도하게 만들기보다 컴팩트하게 구현한다.
- 권장 접근: 여러 기능을 조금씩 걸쳐 만들기보다, 먼저 전체 흐름이 처음부터 끝까지 이어지도록 구현한다. 그런 다음 남은 시간에 어렵거나 핵심이 되는 부분부터 골라 완성도를 끌어올린다.

### 배경

채용 플랫폼에서 실제 채용공고를 가져와 지원자 풀과 매칭·랭킹하는 서비스를 만든다. 개발직 공고에만 한정되지 않고 직군 무관하게 동작해야 한다.

### 데이터 소스

공고 데이터

- 사람인(saramin.co.kr) 채용공고를 비공식 방식으로 크롤링해서 확보한다. 사람인 공식 API(Open API)로 요청하지 않는다.
- 공고 내용이 이미지로 되어 있는 공고를 선택하고, 그 이미지를 파싱해서 공고 내용을 추출한다.
- 공고는 직접 고르되, 범용적인 공고 위주로 선택한다.
- 공고 원문 텍스트를 복사·붙여넣기 하지 않는다. 이미지에서 파싱한 결과가 입력이 되어야 한다.

지원자(목업 이력서) 데이터

- 공고는 2개를 고르고, 각 공고마다 목업 이력서를 6명씩 만든다.
- 구성(공고당): 완벽 매칭형 2명, 부분 매칭형 3명, 미스매칭형 1명.
- 2개 공고는 서로 다른 직군으로 고른다.

### 요구사항

전체 흐름: 공고 크롤링(이미지 공고) → 이미지 파싱으로 내용 추출 → 추출값을 조건으로 바로 세팅 → 매칭 스코어링 실행

1. 사람인 채용공고를 비공식 방식으로 크롤링해서 확보한다 (공식 API 사용 금지). 공고 내용이 이미지로 된 공고를 선택한다.
2. 공고 이미지를 파싱해서 조건을 구조화된 데이터로 추출한다.
3. 지원자별 매칭 점수(0~100점)를 산정하고 랭킹으로 정렬한다.
4. 점수의 근거를 사람이 읽을 수 있는 형태로 함께 제공한다.
5. 직군 무관 일반화. 특정 스킬셋이나 직군을 하드코딩하지 말고, 구조적으로 확장 가능하게 설계한다.
6. CLI 또는 API 엔드포인트 하나로 실행 가능해야 한다.
7. 결과를 확인할 수 있는 간단한 UI를 만든다. 화려할 필요 없이, 매칭 결과와 근거를 보여주는 정도면 충분하다.
8. (구현 불필요) 법적 우회 구조 설계. 채용 정보를 크롤링해서 서비스 제공사가 직접 적재하는 것은 법적으로 문제가 될 수 있다. 데이터가 서비스 제공사가 아니라 고객사를 거쳐서 들어오는 구조를 설계한다. 구현하지 않아도 되고, README에 아키텍처(다이어그램 또는 텍스트 설명)로 정리한다.

### 제출물

- GitHub public 레포 링크 (코드 + README)
- README: 실행 방법과 함께, 설계 결정과 트레이드오프를 반드시 서술한다. 과제를 하면서 든 생각도 편하게 적는다. AI 도구를 활용해도 되지만, README만큼은 최대한 직접 작성한다.
- 직접 만든 목업 이력서 데이터셋
- 최소한의 테스트. 전체 커버리지를 요구하지 않는다. 어떤 케이스를 테스트로 골랐는지를 본다.

### 평가 시 중점적으로 보는 부분

AI 도구(ChatGPT, Copilot, Claude 등)를 적극 활용해서 구현해도 전혀 상관없다. 다만 그 안에서 본인만의 창의성과 아이디어가 드러나는 것이 중요하다. AI가 만들어준 결과물을 그대로 제출하기보다, 문제를 어떻게 정의하고 어떤 판단을 더했는지가 보여야 한다.

### LLM과 외부 API

- LLM이나 외부 API 사용 여부는 자유다.
- 테스트용으로 예산 약 $5의 OpenAI API 키를 받았다. 이 키를 사용한다.
- 키의 값은 이 문서에 적지 않는다. 레포가 public이므로 키는 커밋하지 않고 `.env`에만 둔다.

### 조직과 찾는 사람

- 제품 조직은 1인이 product 개발의 전 과정(목표 설정, 문제 정의, 기획, 개발)에 오너십을 갖고 비즈니스 성과를 만들어오는 사람들로 구성되어 있다.
- 찾는 사람은 "AI 도메인 지식과 활용 능력에 기반하여 문제를 해결하는 SW Engineer"다.
- AI 도메인 지식에 기반하여 문제 해결 전략을 함께 도출하고, 해결하는 과정에서 업무의 경계를 구분짓지 않고 Full Process에 기여할 수 있는 사람이다.
- AI 활용에 필요한 금전적 지원은 모두 해준다.
