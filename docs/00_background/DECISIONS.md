# 00_background 수정 기록

이 폴더의 문서를 수정할 때마다 아래에 기록한다. 형식은 `docs/AGENTS.md`의 "수정 기록"을 따른다.

## 2026-10-10 21:11 — `assignment.md`, `job-posting.md`, `situation.md` 새로 작성

**무엇을 바꿨는지**

- `assignment.md`: 그룹바이가 전달한 과제 안내 HTML의 내용을 항목별로 정리했다. 기본 조건, 배경, 데이터 소스, 요구사항 8개, 제출물, 평가 중점, LLM 사용 조건을 담았다.
- `job-posting.md`: 지원한 채용 공고의 내용을 정리했다. 회사 정보, 찾는 사람, 주요업무, 자격요건, 우대사항, 채용절차를 담았다.
- `situation.md`: 지원자가 누구이고 채용 절차의 어느 단계에 있는지, 기한이 언제인지를 적었다.

**왜 바꿨는지**

- 이 프로젝트는 채용 과제다. 무엇을 만들어야 하고 무엇으로 평가받는지는 과제 안내와 채용 공고에 있다. 이 둘이 `01_problem`부터 뒤따르는 모든 단계의 출발점이므로, 가장 앞 단계인 `00_background`에 먼저 두었다.
- 과제 안내는 요약하지 않고 원문의 조건을 빠짐없이 옮겼다. "공식 API 사용 금지", "원문 텍스트 복사·붙여넣기 금지", "직군 하드코딩 금지"처럼 어기면 안 되는 제약이 많아서, 요약하다가 조건이 빠지면 뒤 단계가 틀린 근거 위에 서게 되기 때문이다.
- 채용 공고를 함께 둔 이유는 평가 기준을 읽기 위해서다. 과제 안내는 "문제를 어떻게 정의하고 어떤 판단을 더했는지"를 본다고 하고, 공고는 "스스로 문제를 정의하고 해결하는 사람"과 "Claude Code를 잘 쓰는 사람"을 찾는다. 과제 안내만으로는 드러나지 않는 평가자의 관점이 공고에 있다.
- 과제 안내 원본에는 OpenAI API 키가 들어 있다. 제출물이 GitHub public 레포이므로 키의 값은 문서에 옮기지 않았고, 원본 HTML 파일도 저장소에 넣지 않았다. 키를 `.env`에 두도록 `.gitignore`에 `.env`를 추가했다.
- 공고 화면에 함께 있던 메뉴, 지도, 취업축하금 안내, FIT 진단 문구는 과제와 무관한 화면 요소라 옮기지 않았다.

**영향을 받는 다른 단계**

- `01_problem`: 과제 안내의 배경과 요구사항을 근거로 풀려는 문제를 정의한다.
- `04_prd`: 요구사항 8개와 제출물 조건이 요구사항분석서의 입력이 된다.
- `14_code`: OpenAI API 키를 `.env`에서 읽어야 하고, 키를 커밋하면 안 된다.

## 2026-10-10 21:12 — `email.md` 새로 작성, `situation.md` 수정

**무엇을 바꿨는지**

- `email.md`: 과제 안내 HTML과 함께 받은 박상민 CSO의 메일을 옮겼다.
- `situation.md`: 미팅 상대가 박상민 CSO라는 것과 과제를 받은 경위를 적었다. 기한을 "전달받은 시점부터 24시간 이내"에서 "소요 최대 24시간, 제출은 월요일(2026-10-12) 자정 전"으로 고쳤다.

**왜 바꿨는지**

- 기한에 대한 정보가 과제 안내와 메일에서 서로 다르다. 과제 안내는 "전달받은 시점으로부터 24시간 이내"라고 하고, 메일은 "소요 최대 24시간, 월요일 자정 전까지"라고 한다. 메일이 지원자에게 직접 보낸 더 구체적인 안내이므로 메일을 기준으로 삼았다. 과제 안내의 문구는 `assignment.md`에 원문대로 남겨 두었다.
- "월요일 자정"은 월요일 0시로도, 월요일 24시로도 읽힌다. 어느 쪽인지 추측해서 적으면 기한을 하루 잘못 잡을 수 있으므로, 확인하지 않았다는 사실을 그대로 적었다.
- 메일의 서명에는 전화번호와 메일 주소가 있다. 제출물이 public 레포이므로 타인의 연락처는 옮기지 않았다.
- 미팅 상대와 채용 공고 작성자가 같은 사람이라는 점을 적은 이유는, 과제를 평가할 가능성이 큰 사람의 관점이 `job-posting.md`에 그대로 드러나 있다는 뜻이기 때문이다.

**영향을 받는 다른 단계**

- `01_problem`: 쓸 수 있는 시간이 최대 24시간이라는 점이 문제의 범위를 정하는 제약이 된다.
- `04_prd`: 기한이 우선순위를 정하는 기준이 된다.

## 2026-10-10 21:15 — 문서 4개를 `background.md` 하나로 합침, "이 과제에서 초점을 두는 것" 추가

**무엇을 바꿨는지**

- `assignment.md`, `job-posting.md`, `email.md`, `situation.md`를 지우고, 그 내용을 `background.md` 하나에 장으로 나눠 담았다. 순서는 지원 상황 → 초점 → 메일 → 과제 안내 → 채용 공고다. 내용은 빼지 않았다.
- 2장 "이 과제에서 초점을 두는 것"을 새로 썼다. 우선순위의 순서를 정직하게 보여준다는 것, 초점이 하네스를 만드는 것과 문제를 잘 해결하는 것이라는 내용이다.

**왜 바꿨는지**

- 사용자가 단계 폴더마다 설계 문서가 하나만 있고, 그 문서가 최신으로 유지되며, 바뀐 내용은 `DECISIONS.md`로 파악하는 구조를 원했다. 파일이 넷이면 무엇이 최신인지와 어디를 읽어야 하는지가 흩어진다. 이 규칙은 `docs/AGENTS.md`의 "문서 규칙"에 적었다.
- 초점은 사용자가 직접 정한 방향이다. 시간이 24시간 내외라 전부 만들 수 없으므로, 무엇을 먼저 했는지가 곧 평가받는 판단이 된다. 과제 안내도 "우선순위를 정해서 진행"하라고 하고 "어떤 판단을 더했는지"를 본다고 한다. 뒤 단계가 범위를 정할 때 근거로 삼도록 배경에 두었다.
- 앞의 두 기록에 나오는 파일 이름(`assignment.md` 등)은 고치지 않았다. 지난 기록은 고치지 않는 것이 규칙이다. 그 파일들의 내용은 지금 `background.md`의 해당 장에 있다.

**영향을 받는 다른 단계**

- `01_problem`: 초점과 시간 제약을 근거로 문제의 범위를 정한다.
- `04_prd`: 우선순위의 순서를 요구사항에 드러낸다.
- `06_data-model`, `07_api`: 하위 폴더로 나누게 되어 있어 "폴더당 문서 하나" 규칙과 맞지 않는다. 아직 고치지 않았다.

## 2026-10-10 21:39 — `background.md`의 기한을 "내려받은 시각부터 24시간 내외"로 고침

**무엇을 바꿨는지**

- 1장의 "기한"을 고쳤다. 기준을 "월요일 자정 전"에서 "과제 파일을 내려받은 2026-10-10 20:22부터 24시간 내외, 곧 2026-10-11 20:22 내외"로 바꿨다.
- "월요일 자정이 0시인지 24시인지 확인하지 않았다"는 문장을 지우고, 따지지 않는 이유를 적었다.

**왜 바꿨는지**

- 사용자가 정했다. 과제가 요구하는 것은 소요 24시간 내외이고, 이것은 누가 재는 것이 아니라 양심으로 지키는 것이다. 그러니 기준은 제출 마감이 아니라 시작 시각이어야 한다.
- 시작 시각으로는 과제 파일을 내려받은 시각을 골랐다. 실제로 과제를 본 시점이기 때문이다.
- 목표 시각(일요일 20:22)이 월요일 자정의 어느 해석보다도 앞선다. 그래서 "자정"의 뜻을 확인할 필요가 없어졌다.

**영향을 받는 다른 단계**

- `01_problem`, `04_prd`: 범위와 우선순위를 정할 때 이 목표 시각을 제약으로 삼는다.

## 2026-10-10 21:39 — `background.md`에 듀데이트를 2026-10-11 20:00으로 확정

**무엇을 바꿨는지**

- 1장의 "기한"에서 "목표는 2026-10-11 20:22 내외"를 "듀데이트는 2026-10-11(일) 20:00"으로 고쳤다.

**왜 바꿨는지**

- "내외"로는 언제 멈출지가 정해지지 않는다. 사용자가 시각 하나로 딱 정하기로 했다.
- 정확히 24시간 뒤는 20:22다. 20:00으로 당긴 것은 남는 22분을 제출 전 마지막 확인(레포를 새로 받아 명령 하나로 실행되는지, API 키가 올라가지 않았는지)과 메일 발송에 쓰기 위해서다. 20:22에 맞추면 확인할 시간이 24시간 밖으로 밀린다.

**영향을 받는 다른 단계**

- `01_problem`, `04_prd`: 범위와 우선순위를 이 듀데이트 안에서 정한다.
