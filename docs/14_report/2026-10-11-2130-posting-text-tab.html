1. 무엇을 검증했는지

사용자가 다시 빌드한 화면(8000번)을 직접 보고 짚었다. 앞 리포트(2026-10-11-2121-screen-review.html)의 P6을 반영한 화면이다.

2. 무엇이 문제인지

  • 오른쪽 칸에 "이력서 원문"과 "공고 원문"이 함께 있다. 사용자가 그렇게 두는 것이 아니라고 했다.
  • 공고 원문은 가운데 칸에 탭으로 있어야 한다. 표현하려는 것은 "이 공고가 이런 조건으로 추출되었다"이다(사용자).
  • 확인한 것: 지금은 조건 하나를 눌러야 그 조건 하나의 자리만 표시된다. 공고에서 무엇이 뽑혔는지 전체가 한눈에 보이지 않는다. 공고 원문은 공고에 대한 것인데 지원자의 이력서와 같은 자리에 있다.

4. 반영 방법

사용자가 방법을 말했으므로 후보를 따로 두지 않는다.

  • 가운데 칸의 맨 위에 탭 둘을 둔다. "조건별 판정"은 지금의 내용이다(지원자의 점수, 조건마다 판정과 근거).
  • "공고 원문"은 공고를 읽은 내용 전체를 보여 주고, 뽑은 담당업무와 조건이 있는 자리를 모두 표시한다. 표시마다 번호(C1, D1)를 붙이고 그룹을 구별한다. 무엇이 어느 그룹으로 뽑혔는지가 한눈에 보인다.
  • 조건을 눌러 오른쪽 칸을 바꾸던 것은 없앤다. 오른쪽 칸은 이력서 원문만 보여 준다.
  • 에이전트가 정한 것: 그룹의 구별은 자격요건과 우대사항은 파란 계열, 참고사항과 담당업무는 회색 계열로 한다. 판정의 색(초록, 주황, 빨강)과 겹치지 않게 하려는 것이다.

5. 반영하다가 나온 것 (2026-10-11 22:30)

  • 확인한 것: 마케팅 공고에서 담당업무 하나(D4)가 공고 원문에 표시되지 않았다. 저장된 항목의 글자는 "ᄂ"(U+1102)이고, 이번 실행에서 다시 읽은 내용의 같은 자리는 "ㄴ"(U+3134)이다. 눈으로는 같은 글자다. 읽기를 다시 하면 결과가 글자 하나 단위로 달라질 수 있다는 뜻이다(앞의 읽기는 3,471자, 이번은 3,469자).
  • 확인한 것: 07_api는 조건이 읽은 내용 안에 있는지를 응답을 만들 때 계산한다고 적었는데, 코드는 특징을 뽑을 때 저장해 둔 값을 그대로 준다. 그래서 읽은 내용이 바뀌어도 값이 따라가지 않는다.
  • 고치는 방법(에이전트가 정했다. 대조의 규칙을 넓히는 것이라 사용자가 확인해야 한다): 대조할 때 띄어쓰기에 더해 유니코드의 표기 차이도 지운다(NFKC 정규화). 서버의 두 대조(조건과 읽은 내용, 근거와 이력서)와 화면이 자리를 찾는 규칙에 똑같이 넣는다. 그리고 in_reading을 설계대로 응답을 만들 때 계산한다. 넘긴 것이 없으면 저장된 값을 쓴다.
  • 영향받는 단계: 03_prd 9.3과 10.1의 대조 규칙, 12_test-scenario의 U1, 13_code.

6. 고친 순서와 결과 (2026-10-11 22:45)

03_prd(F12, 대조 규칙) → 04_wireframe(②, ⑥의 기능 설명) → 09_screen-design(가운데 칸의 탭, 자리를 찾는 규칙) → 12_test-scenario(E8, E10, U1, U10) → 13_code(백엔드의 대조와 응답, 프론트엔드) → result/에 복사하고 다시 빌드.

공고 원문 탭에 뽑은 항목이 모두 표시된다(회계 11곳, 마케팅 12곳). 저장된 판정과 점수는 바뀌지 않았다. 자동 테스트 44개가 통과한다. 그룹의 색과 대조 규칙을 넓힌 것은 에이전트가 정했고 사용자가 확인해야 한다.
