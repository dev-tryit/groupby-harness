# 14_report

검증의 결과를 리포트로 남기는 단계. 리포트가 설계와 코드를 다시 고치는 루프의 출발점이다.

## 언제 만드는가

- 리포트는 코드를 만든 뒤, 사용자가 검증을 시켰을 때만 만든다. 코드를 만들기 전(설계만 하는 동안)에는 리포트를 만들지 않는다.
- 에이전트가 스스로 검증을 시작해서 리포트를 만들지 않는다.
- 사용자가 실행한 화면이나 코드를 직접 보고 고칠 것을 말하는 것도 검증이다. 그때도 바로 고치지 않는다. 사용자가 말한 것을 리포트로 쓰고, 어떻게 고칠지 계획을 적고, 그 리포트로 고친다.

## 흐름

사용자가 검증을 시키면 리포트가 나오고, 사용자가 그 리포트를 어떤 방법으로 반영할지 지시하면 설계 변경에서 코드 변경까지 이어서 진행한다.

1. **검증** — 사용자가 무엇을 검증할지 시킨다.
2. **리포트** — 검증에서 문제가 나오면 리포트 파일을 만들고 경로를 알린다. 여기서 멈춘다. 리포트를 만든 에이전트가 스스로 반영하지 않는다.
3. **지시** — 사용자가 리포트를 읽고, 어떤 방법으로 반영할지를 구체적으로 지시한다.
4. **반영** — 지시받은 방법으로 `00`부터 순서대로 내려오며 영향받는 설계 문서를 고치고, 이어서 코드를 고친다. 역방향으로 건너뛰어 고치지 않는다.
5. **해결** — 설계와 코드가 다시 일치하면 리포트의 상태를 `해결`로 바꾼다.

- 설계만 하는 동안 뒤 단계를 쓰다가 앞 단계를 고쳐야 한다는 것을 알게 되면 리포트를 만들지 않는다. 사용자에게 알리고, 그 앞 단계부터 순서대로 내려오며 고친다(`docs/AGENTS.md`).

## 리포트 파일

- 리포트 하나에 파일 하나. 파일명은 `YYYY-MM-DD-HHMM-<슬러그>.html`이다. 날짜와 시각은 리포트를 만든 시점이다. `commit-reports/`의 보고서와 같은 방식이다.
- 외부 리소스 없이 파일 하나로 열리는 HTML로 쓴다.
- 이 폴더는 `docs/AGENTS.md`의 "단계 폴더 하나에 설계 문서 하나"의 예외다. 리포트는 쌓인다.

## 리포트 내용

간결하게 쓴다.

1. **무엇을 검증했는지** — 누가(어느 에이전트가) 무엇을 어떻게 검증했는지.
2. **무엇이 문제인지** — 문제마다 발견한 곳과 근거. 확인한 것과 추측을 구분한다.
3. **영향받는 단계** — `00`부터 순서대로.
4. **반영 방법의 후보** — 선택지와 추천 후보, 그 이유. 정하는 것은 사용자다.
5. **상태** — 맨 위에 적는다. 처음에는 `미해결`이다.

반영한 뒤에는 사용자가 지시한 방법과 고친 순서를 리포트에 덧붙인다.

## 추적 (TRACKER.md)

`TRACKER.md`는 리포트마다 상태를 확인하는 표다.

- 리포트를 만들면 바로 `TRACKER.md`에 한 줄을 추가하고 상태를 `미해결`로 적는다.
- 사용자가 반영 방법을 지시하면 그 방법을 적는다. 반영이 끝나면 `해결`로 바꾼다.
- 반영하지 않기로 하면 줄을 지우지 않고 `폐기`와 이유를 적는다.
- 단계를 시작할 때 `TRACKER.md`를 읽고, `미해결`로 남은 리포트가 있으면 사용자에게 먼저 알린다.
