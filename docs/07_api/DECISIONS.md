## 2026-10-11 19:35 — `request-response.md`를 요청마다 하는 일, 입력, 출력으로 다시 씀

**무엇을 바꿨는지**

- 요청마다 하는 일, 입력(`~ReqParam`), 출력(`~ResResult`)의 순서로 적었다. 입력과 출력은 필드가 있는 클래스로 두었다. 앞에서는 응답의 예를 JSON으로만 적었고 입력을 따로 적지 않았다.
- 원칙을 늘어놓은 장을 지우고 "한눈에" 표 아래 한 줄로 줄였다. 오류도 `ErrorResResult` 클래스로 적었다.
- 엔드포인트와 필드는 바꾸지 않았다.
- `AGENTS.md`에 "요청과 응답으로 기술한다" 장을 더했다.

**왜 바꿨는지**

- 사용자가 API는 요청에 대해 `reqParam`, `resResult` 같은 형식으로 클래스를 두고, 요청과 응답을 보는 데 집중해야 한다고 했다. 요청이 무슨 일을 하고 입력이 무엇이고 출력이 무엇인지로 기술하는 것이다.

**영향을 받는 다른 단계**

- `10_security`: 오류의 장 번호가 3장에서 5장으로 바뀌어 가리키는 곳을 고쳤다.
- `09_screen-design`: 필드가 그대로라 고칠 것이 없다.
- `13_code`: 입력과 출력의 클래스 이름을 이대로 쓴다.

## 2026-10-11 20:15 — 앞 단계의 키에 맞춤 (`request-response.md`, `external.md`)

**무엇을 바꿨는지**

- 지원자 한 명의 요청을 `GET /api/postings/{posting_id}/resumes/{resume_id}`에서 `GET /api/resumes/{resume_id}`로 바꿨다. 입력에서 `posting_id`가 빠졌다.
- 조건과 담당업무의 `id`를 `item_id`와 `no`로 나눴다. 판정의 `condition_id`를 `item_id`로 바꿨다.
- `external.md`: LLM과는 `no`(C1, C2)를 주고받고, 코드가 `item_id`로 바꾼다고 적었다.

**왜 바꿨는지**

- 앞 단계 `06_data-model/persistent`에서 1:N인 자식이 자기만의 PK를 갖게 되었다. `resume_id`가 전체에서 고유하므로 경로에 공고 번호가 필요 없다.
- LLM에게 뜻이 없는 긴 `item_id`를 주지 않는 이유: 짧은 번호가 틀릴 일이 적고, 지금의 프롬프트가 그렇게 쓴다.

**영향을 받는 다른 단계**

- `09_screen-design`: 요청의 경로와 필드.
- `10_security`: 경로를 예로 든 시나리오.

## 2026-10-11 20:18 — 랭킹의 응답에 조건마다의 판정을 더함 (`request-response.md` 3장)

**무엇을 바꿨는지**

- `RankedResume`에 `verdicts`(조건마다 `item_id`와 `mark`)를 더했다.

**왜 바꿨는지**

- 화면의 랭킹에서 지원자를 펼치지 않고도 어느 조건이 일치이고 어느 조건이 다름인지 보이게 하려는 것이다. 브랜딩의 첫 원칙(판정과 근거가 먼저 보인다)에서 나왔다(`05_branding/DECISIONS.md`).
- 근거(구절, 생각, 이력서 원문)는 여전히 지원자 한 명의 요청에서만 준다. 랭킹의 응답이 무거워지지 않는다.
- `mark`는 저장하지 않고 응답을 만들 때 계산하는 값이다. 랭킹을 낼 때 이미 이력서 원문과 근거를 대조해야 점수가 나오므로 더 드는 계산이 없다.

**영향을 받는 다른 단계**

- `09_screen-design`: 랭킹의 줄.
