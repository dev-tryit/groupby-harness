# 06_data-model

데이터 모델 단계. 서비스를 데이터로 바라본다.

ERD만으로는 충분하지 않다. 데이터를 성격에 따라 세 폴더로 나눈다.

| 폴더 | 데이터의 성격 | `08_infra`에서 고르는 기술 |
| :- | :- | :- |
| `persistent/` | 영속 데이터. 계속 보관하는 데이터와 그 관계. ERD는 여기에 둔다. 이미지나 첨부 파일처럼 파일로 보관하는 데이터도 여기서 다룬다. | DB, 파일 저장소 |
| `volatile/` | 휘발성 데이터. 잠깐 쓰고 사라져도 되는 데이터 (캐시, 세션, 카운터 등). | 메모리 DB |
| `event/` | 이벤트. 한쪽에서 발생해 다른 쪽으로 전달되는 데이터. | pub/sub |

- 데이터마다 예상되는 양을 적는다. 근거는 `03_prd`의 사용자와 요청 규모다. 이 양이 `08_infra`의 근거가 된다.
- 이 단계에서는 어떤 데이터가 있고 어떤 성격인지만 정한다. 특정 기술(PostgreSQL, MongoDB 등)에 맞춘 구조는 쓰지 않는다. 그것은 `08_infra`에서 정한다.
- 데이터 모델은 UML 다이어그램으로 표현한다. 직관적으로 보이게 하려는 것이다. 설명은 최소한으로 쓴다.
- 다이어그램의 데이터마다 필드를 적는다. 기본 키(PK)와 외래 키(FK)도 표시한다.
- 다이어그램에는 반드시 왜 이렇게 구성했는지의 근거를 함께 적는다. 데이터를 나누거나 합친 것, 관계, 키마다 근거가 있어야 한다. 근거가 없는 구성은 두지 않는다.
- 저장해야 하는 것만 저장한다. 아무것이나 저장하지 않는다. 필드마다 왜 저장하는지의 기준이 있어야 하고, 기준에 맞지 않는 것은 저장하지 않는다. 다른 데이터에서 계산되는 값은 저장하지 않는다.
- 구성은 데이터를 어떻게 읽는지(조인)를 고려해서 짠다. 읽는 일마다 어느 데이터를 어느 키로 잇는지를 적고, 구성이 그 읽는 길에 맞는지를 보인다.

## 키와 관계 테이블을 판단하는 조건

관계가 무엇이냐(1:1, 1:N, M:N)에 따라 정한다.

| 관계 | 구조 | 이유 |
| :- | :- | :- |
| 1:1 | 부모의 PK를 자식의 PK이자 FK로 쓴다 | PK는 중복될 수 없으므로 1:1이 구조로 보장된다. 관계 테이블을 두면 테이블이 셋이 되어 조인이 늘어난다 |
| 1:N | 자식이 자기 PK를 갖고, 부모의 키는 FK로 둔다 | 부모의 키가 자식에 여러 번 들어가야 한다 |
| M:N | 관계 테이블을 만든다. 양쪽의 FK를 합친 것이 PK다 | 두 테이블을 직접 이을 수 없다 |

- 나중에 관계가 바뀔지 모른다는 이유로 관계 테이블을 미리 만들지 않는다. 지금의 관계에 맞게 짜고, 바뀌면 그때 구조를 바꾼다.
- 예외는 하나다. 관계가 넓어지는 것이 이미 확정되어 있으면 처음부터 그 관계에 맞게 짠다.
