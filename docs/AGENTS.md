# docs

설계 문서와 코드를 단계별로 담는 폴더.

## 단계 구조

| 폴더 | 내용 |
| :- | :- |
| `00_context` | 컨텍스트 |
| `01_problem` | 문제 정의 |
| `02_research` | 조사 |
| `03_prd` | 요구사항분석서와 핵심 알고리즘 (성능) |
| `04_wireframe` | 와이어프레임 (큰 그림 보기) |
| `05_branding` | 브랜딩 |
| `06_data-model` | 데이터 모델 (데이터로 바라보기) |
| `07_api` | API 구조 |
| `08_infra` | 인프라 구조 |
| `09_screen-design` | 화면설계도 (프론트 코드를 만들기 위한 그림) |
| `10_security` | 보안 (안전) |
| `11_log` | 로그 설계 |
| `12_test-scenario` | 테스트 시나리오 (코드 완성 조건) |
| `13_code` | 실제 코드 |
| `14_report` | 리포트 (검증 결과와 분석 내용) |

비어 있는 하위 폴더에는 `.gitkeep`을 둔다. git은 빈 폴더를 기록하지 않기 때문이다. 폴더에 첫 파일을 넣으면 `.gitkeep`을 지운다.

단계 폴더에 `AGENTS.md`가 있으면 그 단계의 목적과 고유 규칙이 거기에 있다. 그 단계를 작업하기 전에 읽는다.

## 문서 규칙

- 단계 폴더 하나에는 설계 문서가 하나만 있다. 내용을 여러 파일로 나누지 않고, 한 문서 안에서 장으로 나눈다.
- 설계 문서의 이름은 폴더 이름에서 번호를 뺀 것이다. 예를 들어 `00_context/context.md`다.
- 단계 폴더가 하위 폴더로 나뉘어 있으면 설계 문서는 하위 폴더에 쓴다. 이때도 폴더 하나에 문서 하나다. 예를 들어 `06_data-model/persistent/persistent.md`다. `DECISIONS.md`는 단계 폴더에 하나만 둔다.
- 설계 문서는 항상 최신 내용만 담는다. 무엇이 왜 바뀌었는지는 문서가 아니라 `DECISIONS.md`에서 파악한다.

## 번호 규칙

- 단계 번호는 서로 겹치면 안 된다. 번호가 곧 진행 순서이므로, 한 번호에는 폴더가 하나만 있다.
- 단계를 추가하거나 순서를 바꾸면 번호를 다시 매기고, 이 표와 다른 `AGENTS.md`에 적힌 폴더 이름을 모두 함께 고친다.

## 진행 원칙

- 단계는 번호 순서대로 진행한다. 앞 단계의 산출물이 뒤 단계의 입력이 된다.
- 뒤 단계를 작성할 때는 앞 단계의 산출물을 먼저 읽고 그것을 근거로 쓴다.
- 앞 단계를 고치면 그 영향을 받는 뒤 단계와 코드도 순서대로 함께 고친다.
- `12_test-scenario`의 테스트 시나리오가 코드의 완성 조건이다. 시나리오를 통과해야 그 기능이 끝난 것이다.
- 코드를 고치면 설계 문서를 바로 고치지 않는다. 먼저 `14_report`에 리포트를 쓴다.
- 뒤 설계 단계를 작성하다가 앞 단계를 고쳐야 한다는 것을 알게 되면, 뒤 단계의 문서로 앞 단계를 고치지 않는다. 사용자에게 알리고, 고쳐야 하는 앞 단계로 올라가 거기서부터 순서대로 내려오며 고친다. 예를 들어 `10_security`의 대책이 `07_api`를 고쳐야 하는 경우다. 이때는 리포트를 만들지 않는다. 리포트는 코드를 만든 뒤 사용자가 검증을 시켰을 때만 만든다.
- 리포트를 어떻게 반영할지는 사용자가 지시한다. 지시를 받은 뒤 `00`부터 순서대로 내려오며 영향받는 문서를 고치고, 이어서 코드를 고친다. 역방향으로 건너뛰어 고치지 않는다. 절차와 리포트 파일의 규칙은 `14_report/AGENTS.md`에 있다.
- 리포트마다 맨 위에 상태를 적는다. 처음에는 `미해결`이다. `00`부터 내려오며 영향받는 문서를 모두 고쳐 설계와 코드가 다시 일치하면 `해결`로 바꾼다.
- 리포트가 `미해결`인 동안에는 설계와 코드가 어긋나 있어도 된다. 리포트가 `해결`되면 그 루프는 끝난다.

## 검증

- 설계와 코드는 같은 에이전트가 맡는다. 문맥을 아는 에이전트가 설계하고 코드를 짜야 하기 때문이다.
- 검증은 만든 에이전트가 하지 않는다. 만들지 않은 에이전트가 한다.
- 검증은 에이전트 팀으로 한다. 에이전트 하나가 모든 것을 신경 쓸 수 없기 때문이다.
- 검증 서브에이전트는 단계 폴더 단위로 만든다. 서브에이전트는 그 폴더의 내용을 바탕으로 전문가 역할을 받아 검증한다. 예를 들어 `10_security` 서브에이전트는 보안 전문가로서 검증한다.
- 검증 결과는 `14_report`에 리포트로 쓴다. 그 리포트를 읽고 `00`부터 다시 루프를 돈다.
- 검증은 코드를 다 만든 뒤에 한다. 세부 방식은 그때 사용자가 정한다. 아직 정해지지 않았다.

## 수정 기록 (DECISIONS.md)

각 단계 폴더에는 `DECISIONS.md`가 있다. 그 폴더의 문서를 수정할 때마다 왜 수정했는지를 그 폴더의 `DECISIONS.md`에 기록한다.

- 중요한 것은 길이가 아니라, 왜 수정했는지를 충분히 설명하는가이다. 간결하게 쓰되 이유가 빠지거나 모호해지면 안 된다.
- 문서를 수정한 것과 같은 작업 안에서 기록한다. 나중으로 미루지 않는다.
- 새 기록은 파일 맨 아래에 추가하고, 지난 기록은 고치지 않는다.
- 기록 하나에는 다음을 담는다.
  - 날짜와 시각, 수정한 문서
  - 무엇을 어떻게 바꿨는지
  - 왜 바꿨는지 (계기, 근거가 된 앞 단계 산출물이나 `14_report`의 분석, 검토한 대안과 버린 이유)
  - 이 수정으로 영향을 받는 다른 단계
