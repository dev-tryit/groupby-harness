# groupby-harness

그룹바이에이치알 채용 과제 "지원자-공고 매칭 스코어링 엔진"을 수행하는 저장소입니다.

> 이 문서는 과제를 진행하면서 계속 채워 나가는 중입니다. 아직 만들지 않은 부분은 "작성 예정"으로 표시했습니다.

## 실행 방법

코드는 서브모듈로 나뉘어 있어서, 아래처럼 받아야 합니다. 그냥 받으면 코드 폴더가 비어 있습니다.

```bash
git clone --recursive -b v1.0.0 https://github.com/dev-tryit/groupby-harness.git
```

실행하려면 OpenAI API 키가 필요합니다. 키는 저장소에 넣지 않았습니다. 과제와 함께 주신 키를 프로젝트 루트의 `.env` 파일에 넣어 주세요.

```bash
OPENAI_API_KEY=여기에_키를_넣습니다
```

실행 명령은 작성 예정입니다. 코드는 `docs/14_code/`에 있습니다.

## 폴더 구성

어디에 무엇이 있는지입니다.

```
README.md              이 문서
AGENTS.md              에이전트가 매 세션 읽는 지침 (전체에 항상 적용되는 것만)
CHECKLIST.md           지금 정하지 않고 뒤 단계에서 정하기로 한 것
commit-reports/        커밋 전 보고서와 커밋 반영 추적
docs/
  00_context ~ 12_log      설계 문서. 단계마다 설계 문서 하나와 수정 기록(DECISIONS.md) 하나
  13_test-scenario/        테스트 시나리오 (코드 완성 조건)
    golden-set/            목업 이력서 데이터셋
  14_code/                 코드
    frontend/              서브모듈 → dev-tryit/groupby-frontend
    backend/               서브모듈 → dev-tryit/groupby-backend
    infra/                 서브모듈 → dev-tryit/groupby-infra
  15_report/               리포트 (검증 결과와 분석 내용)
```

보시려는 것에 따라 이렇게 찾으시면 됩니다.

| 보시려는 것 | 위치 |
| :- | :- |
| 코드 | `docs/14_code/` (GitHub에서는 폴더를 누르면 해당 레포로 이동합니다) |
| 목업 이력서 데이터셋 | `docs/13_test-scenario/golden-set/` |
| 설계 결정의 이유 | 각 단계 폴더의 `DECISIONS.md` |
| 에이전트에게 준 규칙 | 각 폴더의 `AGENTS.md` |

왜 이렇게 짰는지입니다. 자세한 설명은 아래 "하네스"에 있습니다.

| 구성 | 이유 |
| :- | :- |
| `docs/`를 번호 단계로 나눔 | 앞 단계의 산출물이 뒤 단계의 입력이 되도록, 번호가 곧 진행 순서입니다. |
| 코드가 `docs/14_code/`에 있음 | 코드도 루프의 한 단계입니다. 코드를 고치면 리포트를 쓰고 `00`부터 다시 내려오므로, 설계 단계와 같은 줄에 번호를 붙여 두었습니다. |
| 단계마다 설계 문서 하나와 `DECISIONS.md` 하나 | 문서는 최신 내용만 담고, 무엇이 왜 바뀌었는지는 수정 기록에서 파악합니다. |
| 폴더마다 `AGENTS.md` | 에이전트가 그 폴더에서 작업할 때만 읽게 해서 불필요한 토큰을 쓰지 않습니다. |
| 목업 이력서가 `13_test-scenario/golden-set/`에 있음 | 이력서는 정답지입니다. 코드보다 앞 단계에 두어 코드에 맞춰 고치지 못하게 했습니다. |
| `frontend/`, `backend/`, `infra/`를 폴더로 나눔 | 서로 얽혀 스파게티 코드가 되는 것을 막습니다. |
| 세 폴더를 서브모듈(별도 레포)로 나눔 | 코드 레포를 각각 관리하고, GitHub Actions를 환경마다 다르게 설정하기 위해서입니다. |
| `commit-reports/`가 `docs/`와 나란히 있음 | 커밋 보고서는 설계 단계가 아니라 커밋 절차에 속합니다. |

## 이 과제에서 초점을 둔 것

주어진 시간은 24시간 내외입니다. 전부 만들 수 없기 때문에, 무엇을 먼저 했는지가 곧 저의 우선순위입니다. 저는 두 가지에 초점을 두었습니다.

1. **앞으로 개발할 때 계속 활용할 하네스를 만드는 것**
2. **문제를 잘 해결하는 것**

우선순위가 곧 답안입니다. 그래서 무엇을, 왜, 어떻게 했는지를 보여주는 것에 집중했습니다.

코드를 먼저 쓰지 않고 하네스부터 만든 것은 의도한 순서입니다. 그 순서는 커밋 기록에 그대로 남아 있습니다.

## 하네스

에이전트(Claude Code)가 일하는 틀을 폴더 구조와 지침 파일로 만들었습니다.

### 설계에서 코드까지 한 방향으로 흐르는 루프

`docs/`를 `00`부터 `15`까지 단계로 나누었습니다. 앞 단계의 산출물이 뒤 단계의 입력이 됩니다.

| 단계 | 내용 |
| :- | :- |
| `00_context` | 컨텍스트 |
| `01_problem` | 문제 정의 |
| `02_research` | 조사 |
| `03_branding` | 브랜딩 |
| `04_prd` | 요구사항분석서 |
| `05_wireframe` | 와이어프레임 |
| `06_data-model` | 데이터 모델 |
| `07_api` | API 구조 |
| `08_algorithm` | 핵심 알고리즘 |
| `09_infra` | 인프라 구조 |
| `10_screen-design` | 화면설계도 |
| `11_security` | 보안 |
| `12_log` | 로그 설계 |
| `13_test-scenario` | 테스트 시나리오 (코드 완성 조건) |
| `14_code` | 실제 코드 |
| `15_report` | 리포트 (검증 결과와 분석 내용) |

- 코드를 고쳐도 설계 문서를 바로 고치지 않습니다. `15_report`에 리포트를 쓰고, 그것을 읽고 `00`부터 다시 내려오며 고칩니다. 설계와 코드가 서로를 제멋대로 고치면 무엇이 기준인지 알 수 없게 되기 때문입니다.
- 조사보다 문제 정의가 먼저입니다. 무엇을 풀지 모르고 조사할 수 없기 때문입니다.
- 데이터와 통신은 성격을 먼저 정하고, 기술은 그 뒤 `09_infra`에서 고릅니다.

### 단계 폴더마다 설계 문서 하나와 수정 기록 하나

- 단계 폴더에는 설계 문서가 하나만 있고, 항상 최신 내용만 담습니다.
- 무엇이 왜 바뀌었는지는 같은 폴더의 `DECISIONS.md`에 쌓입니다. 짧게 쓰는 것보다 왜 수정했는지를 충분히 설명하는 것을 기준으로 삼았습니다.

### 지침은 폴더마다 나누고 필요할 때만 읽는다

지침 파일(`AGENTS.md`)을 폴더마다 나누어 두었습니다. 에이전트는 그 폴더에서 작업할 때만 그 지침을 읽습니다. 불필요한 토큰을 쓰지 않기 위해서입니다.

### 커밋은 사람이 두 번 허용한다

에이전트가 임의로 커밋하지 않습니다. 에이전트가 추천하고, 제가 허용하면 간결한 HTML 보고서를 만들고, 제가 그것을 읽고 다시 허용해야 커밋합니다. 커밋은 기능 단위로 합니다. 보고서는 `commit-reports/`에 있고, 커밋에 반영되었는지는 `commit-reports/TRACKER.md`로 추적합니다.

### 만든 에이전트와 검증하는 에이전트를 나눈다

- 설계와 코드는 같은 에이전트가 맡습니다. 문맥을 아는 쪽이 설계하고 코드를 짜야 하기 때문입니다.
- 검증은 만들지 않은 에이전트가 합니다.
- 에이전트 하나가 모든 것을 신경 쓸 수 없으므로 검증은 에이전트 팀으로 합니다. 단계 폴더마다 서브에이전트를 두고, 그 폴더의 내용을 바탕으로 전문가 역할을 주어 검증하게 합니다.

검증 팀은 아직 만들지 않았습니다. 작성 예정.

### 코드 구조

- 헥사고날 아키텍처로 씁니다. 테스트가 쉽기 때문입니다.
- 프론트엔드, 백엔드, 인프라를 처음부터 폴더로 나눕니다(`frontend/`, `backend/`, `infra/`). 서로 얽혀 스파게티 코드가 되면 나중에 리팩토링할 때 서로에게 미치는 영향을 파악할 수 없기 때문입니다.
- 세 폴더는 각각 별도 레포이고 서브모듈로 연결했습니다([frontend](https://github.com/dev-tryit/groupby-frontend), [backend](https://github.com/dev-tryit/groupby-backend), [infra](https://github.com/dev-tryit/groupby-infra)). 코드 레포를 각각 관리하기 위해서이고, GitHub Actions를 환경마다 다르게 설정할 일이 많기 때문입니다.
- 인프라는 `infra/local/`(Docker Compose)과 `infra/server/`(Pulumi)로 나눕니다. 이번 과제는 로컬 구성만 만들기로 했고(아직 만들지 않았습니다), `infra/server/`는 비워 두고 이유만 적었습니다. 평가하는 분이 자기 컴퓨터에서 명령 하나로 실행할 수 있어야 하는데, 클라우드에 의존하면 계정과 키가 필요해지기 때문입니다.
- 로그는 형태를 한 번 정하고 프론트엔드와 백엔드가 같이 씁니다. 모든 로그에 trace id를 넣습니다. 메시지의 형태가 일관되어야 흐름을 파악하기 쉽기 때문입니다.

### 브랜치와 CI/CD

- 브랜치 전략은 Git Flow입니다(`main`, `dev`, 버전 브랜치 `v1.0.0`·`v1.1.0`…, `feature/~`, `hotfix/~`).
- 브랜치를 이렇게 나누는 이유는 CI/CD입니다. GitHub Actions가 브랜치에 따라 테스트와 배포를 돌립니다.
- 이번 과제에서는 CI/CD와 `dev`·`feature/~`·`hotfix/~` 브랜치를 구성하지 않았습니다. 클라우드에 올리지 않아 배포할 곳이 없기 때문입니다. 지금 개발 중인 버전이 `v1.0.0`이므로 `v1.0.0` 브랜치에서 개발했습니다.

## 문제 정의

자세한 내용은 `docs/01_problem/problem.md`에 있습니다. 문제 정의에서는 어떻게 풀지를 정하지 않고, 어떤 문제를 풀어야 하는지에 집중했습니다.

공고(비정형 이미지)에서 조건을 뽑고, 그 조건과 이력서를 비교해 지원자가 조건을 충족하는지 판정하고, 사람이 확인할 수 있는 점수와 근거를 내는 문제입니다.

```
[공고]    수집 → 읽기 → 조건 추출 ─┐
                                   ├→ 비교(판정) → 점수 → 근거 → 사람의 판단 → 데이터
[이력서] ──────────────────────────┘        ↑                                   │
                                             └──────── 검증과 개선 ──────────────┘
```

| 단계 | 풀어야 하는 문제 |
| :- | :- |
| 1. 수집 | 사람인의 이미지 공고를 공식 API 없이 가져와야 합니다. |
| 2. 읽기 | 이미지에 적힌 내용을 틀리지 않게 읽어야 합니다. |
| 3. 조건 추출 | 읽은 내용에서, 어떤 직군의 공고든 조건을 뽑아야 합니다. |
| 4. 비교(판정) | 공고의 조건과 이력서를 비교해, 표현이 달라도 지원자가 조건을 충족하는지 알아야 합니다. |
| 5. 점수 | 판정을 사람이 납득할 수 있는 0~100점으로 만들어야 합니다. |
| 6. 근거 | 근거마다 출처(공고의 어느 조건, 이력서의 어느 구절)를 가리켜, 사람이 직접 확인할 수 있어야 합니다. |
| 7. 검증 | 근거가 사실인지, 점수가 그 근거에서 나왔는지를 확인할 수 있어야 합니다. |
| 8. 피드백 | 사람이 근거를 보고 내린 판단이 데이터로 남아, 다음 검증과 개선에 쓰여야 합니다. |

전체에 걸친 제약은 세 가지입니다. 직군 무관(특정 직군이나 스킬에 기대지 않음), 비용(약 $5 안에서 개발과 평가자의 실행), 법(데이터가 고객사를 거쳐 들어오는 구조)입니다.

문제를 이렇게 본 이유입니다.

- **조건이 중심축입니다.** 공고를 넣으면 조건이 자동으로 만들어지고, 점수와 근거는 그 조건을 기준으로 나옵니다.
- **직군이 아니라 조건의 형식을 일반화해야 합니다.** 세상에 어떤 직군이 얼마나 있는지 알 수 없기 때문입니다. 그래서 어떤 공고에서든 유의미한 특징을 뽑아내는 특징 추출기가 필요합니다.
- **점수는 사람이 납득할 수 있는 수치여야 합니다.** LLM이 내놓은 숫자는 그럴듯한 말일 뿐 실제 수치가 아닙니다.
- **매칭에는 객관적인 정답이 없습니다. 그래서 근거가 중요합니다.** 풀어야 하는 문제는 "맞음을 증명한다"가 아니라 "사람이 확인할 수 있게 한다"입니다.
- **골든셋은 정답이 아니라 가설을 증명하는 데이터입니다.** 사람의 판단과 일치하는지는 이 과제 안에서 증명할 수 없습니다.

아직 정하지 않은 것(조건의 종류, 점수의 뜻, LLM을 쓰는 곳 등)은 조사한 뒤에 정합니다. 작성 예정.

## 하지 않은 것과 그 이유

작성 예정. 시간 안에 하지 않기로 한 것과, 시간이 더 있었다면 다음에 할 것을 순서대로 적습니다.

| 하지 않은 것 | 이유 | 다음에 한다면 |
| :- | :- | :- |
| 서버(클라우드) 인프라 | 평가하는 분이 자기 컴퓨터에서 명령 하나로 실행해야 합니다. 클라우드에 의존하면 계정과 키가 필요해집니다. | `infra/server/`에 Pulumi로 작성하고, 백엔드는 저장소 어댑터만 바꿉니다. |
| GitHub Actions CI/CD와 `dev`·`feature/~`·`hotfix/~` 브랜치 | 클라우드에 올리지 않아 배포할 곳이 없습니다. | `feature/~`에서 테스트, `dev`와 `main`에서 배포를 돌립니다. |

## 목업 이력서 데이터셋

작성 예정. 과제가 정한 이력서 구성(공고당 완벽 매칭형 2명, 부분 매칭형 3명, 미스매칭형 1명)은 골든셋입니다. `docs/13_test-scenario/golden-set/`에 둡니다.

- 골든셋은 검증하려는 가설을 증명하는 데이터여야 합니다. 그래서 골든셋을 구축하는 일을 중요하게 보았습니다.
- 골든셋은 테스트 시나리오(코드 완성 조건)가 쓰는 정답지입니다. 코드를 짜기 전에 확정하고, 코드의 결과에 맞춰 고치지 않습니다. 그래서 코드 폴더가 아니라 코드보다 앞 단계에 두었습니다.
- 완성 조건은 순위 하나가 아니라 크롤링부터 UI까지 전체 흐름입니다.

## 법적 우회 구조 설계

작성 예정. 서비스 제공사가 사람인의 데이터를 직접 가져가 적재하면 법적으로 문제가 될 수 있습니다. 데이터가 고객사를 거쳐 들어오는 구조가 어떻게 동작하는지를 시퀀스 다이어그램으로 보여줍니다.

## 과제를 하면서 든 생각

작성 예정.

- 매칭이 옳은지는 어떻게 증명할 수 있는가를 고민했습니다. 매칭에는 객관적인 정답이 없고, 골든셋은 제가 붙인 딱지입니다. 진짜 검증은 사람들에게 물어야 합니다. 그래서 점수보다 근거가 중요하다고 보았습니다.
- 검증까지 가고 그 결과를 나중에 데이터로 쓰려면, 사람의 판단을 받는 UI/UX까지 표현해서 데이터 플라이휠이 굴러가게 만들어야 한다고 생각했습니다.
