# commit-reports

커밋 규칙과 절차, 그리고 커밋 전에 사용자가 확인하는 HTML 보고서를 두는 폴더.

## 커밋 규칙

불필요한 코드가 커밋되는 것을 막기 위해 기능 단위로 커밋한다.

- 커밋 하나에는 기능 하나만 담는다. 서로 다른 기능이나 무관한 수정을 한 커밋에 섞지 않는다.
- 그 기능에 대한 `docs/15_report`의 리포트가 모두 `해결` 상태일 때만 커밋을 추천한다. `미해결` 리포트가 남아 있으면 커밋하지 않는다.
- 설계 문서만 담은 커밋도 허용한다. 코드가 아직 없는 설계 단계에서는 설계만 커밋한다.
- `git add .`나 `git add -A`를 쓰지 않고, 그 기능에 속한 파일만 경로를 지정해 스테이징한다.
- 커밋 전에 `git diff --staged`로 스테이징된 내용을 확인하고, 디버그 코드·임시 파일·기능과 무관한 변경이 있으면 뺀다.
- 한 파일에 여러 기능의 변경이 섞여 있으면 기능별로 나눠서 커밋한다.

## 커밋 절차 (필수)

사용자의 허용을 두 번 받는다. 어느 단계든 명시적인 허용 없이 다음 단계로 넘어가지 않는다.

1. **추천** — 커밋할 만한 기능 단위가 생기면 무엇을 커밋할지 사용자에게 추천한다. 여기서 멈춘다.
2. **첫 번째 허용** — 사용자가 추천을 허용하면 그때 HTML 보고서를 만들고 경로를 알린다. 허용 전에는 보고서를 만들지 않는다.
3. **두 번째 허용** — 사용자가 보고서를 읽고 허용하면 그때 커밋한다. 수정 요청이 있으면 코드와 보고서를 함께 고친 뒤 다시 허용을 받는다.

## 보고서 파일

- 커밋 하나에 보고서 하나. 파일명은 `YYYY-MM-DD-HHMM-<기능-슬러그>.html`이다. 날짜와 시각은 보고서를 만든 시점이다.
- 외부 리소스 없이 파일 하나로 열리는 HTML로 쓴다.
- 보고서는 해당 기능 커밋에 함께 포함한다.

## 추적 (TRACKER.md)

`TRACKER.md`는 보고서마다 커밋에 반영되었는지를 확인하는 표다.

- 보고서를 만들면 바로 `TRACKER.md`에 한 줄을 추가하고, 커밋 반영을 `미반영`으로 적는다.
- 커밋한 직후에 그 줄을 `반영`으로 바꾸고 커밋 해시를 적는다.
- 이 `TRACKER.md` 갱신은 따로 커밋하지 않고 다음 커밋에 함께 넣는다. "무관한 수정을 섞지 않는다"는 커밋 규칙의 유일한 예외다.
- 커밋을 추천하기 전에 `TRACKER.md`를 읽고, `미반영`으로 남은 보고서가 있으면 사용자에게 먼저 알린다.
- 보고서가 폐기되면 줄을 지우지 않고 `폐기`로 적는다.

## 보고서 내용

간결하게, 한 화면에 들어오는 분량으로 아래 네 가지만 쓴다.

1. **무엇을** — 어떤 기능을 수정했는지 한두 문장.
2. **왜** — 수정한 이유.
3. **어떻게** — 수정 방식의 핵심만 3~5줄.
4. **변경 파일** — 파일 경로와 한 줄 설명.

구현 세부, 대안 비교, 배경 설명은 쓰지 않는다. 심층 논의는 사용자가 읽은 뒤 대화로 한다.
